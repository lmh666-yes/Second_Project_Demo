## 1. 系统组成与数据流

三个部分，两块 STM32F407 开发板（板1 STM32F407ZE、板2 STM32F407ZG）加一台 PC。

```
传感器 → 板1 检测端 →(LoRa 433M)→ 板2 数据通信端 →(USART2/RS232)→ PC 上的 Qt 上位机
                                        ├→(USART3/ESP8266)→ MQTT 服务器
                                        ├→(RS485/Modbus)→ 其他从机
                                        └→(SPI1)→ W25Q128 Flash 断网缓存
```

数据流的方向与责任人：

1. 板1 周期性采集温度、湿度、气压、光照、TVOC、MQ135 原始值，按 20 字节环境帧封包，经 LoRa 发往板2。当前只有温湿度是实测值，其余四项固定填 0（见 4.2）。
2. 板2 收到环境帧后逐条校验长度、帧头 `AA 55`、帧尾 `55 AA`、命令字 0x01 与长度字段 0x0C、CRC16，共 6 条判断（`B2\main.c:932-940`），全部通过才入队。
3. 板2 的转发任务把帧写进 W25QXX 缓存，并通过 USART2 转发给 Qt 上位机；断网期间积压的记录由补传任务按原始时间戳回传（见 5.3）。
4. Qt 上位机解析帧、刷新卡片与曲线、判定告警、可存 CSV。
5. Qt 上位机也可以下发控制命令（0x10~0x14、0x16）给板2，板2 回应答，用于查询状态、开关转发与缓存、清缓存、重启板2、启停历史数据补传。

设计上的三条分工界线：

- 板1 只管采集与上报，不处理告警、不存历史、不联外网。这样板1 的故障面小，掉线也只影响数据新鲜度。
- 板2 只管通信与缓存，不改动环境帧内容，原样转发。这样上位机看到的字节与板1 发出的字节一致，便于逐字节比对排查。
- 告警判定、阈值、历史记录全部放在上位机。阈值可以随时改，不需要重烧固件。

### 2.5 运行期引脚冲突检测

`FWLIB` 里的 `gpio_core` 提供 `GPIO_Claim`（每个 `GPIO_*InitEx` 里登记）与 `GPIO_ClaimDump()`。冲突会立刻打印：

```
[GPIO_Claim] CONFLICT A2 : xxx.c:NN  vs  yyy.c:MM
```

`vs` 两侧各有两个空格，源字符串在 `B2\FWLIB\src\gpio_core.c:139`。

`GPIO_ClaimDump()` 在两块板的 `main()` 里调用（所有自检跑完、调度器尚未启动）：板1 `B1\main.c:1029`、板2 `B2\main.c:1633`。验收时看的目标行是 `==== target : conflict 0 / lost 0 ====`（`B2\FWLIB\src\gpio_core.c:226`）。库内声明的同脚见 2.4 的清单，靠选用模块来规避，不是运行期报错。

引脚事实有三个互相独立的来源，排查时可以对：

1. `main.c` 顶部的引脚占用表（板1 `B1\main.c:52-83`、板2 `B2\main.c:56-87`）。
2. 静态扫描脚本 `本地工具\仓库巡检\pin_audit.py`，扫 `FWLIB\inc\*.h` 里的 `*_PORT` / `*_PIN` 宏。
3. 运行期 `GPIO_ClaimDump()` 的输出。

### 2.7 看门狗

- IWDG 超时 4000 ms（`APP_WDG_TIMEOUT_MS`，`B1\main.c:109`、`B2\main.c:123`；`SYS_WDG_Init` 在 `B1\main.c:1065`、`B2\main.c:1685`）。

## 3. 通信协议

### 3.1 帧格式

```
AA 55 | CMD | LEN | DATA(LEN 字节) | CRC_LO CRC_HI | 55 AA
```

| 字段 | 长度 | 说明 |
|---|---|---|
| 帧头 | 2 | 固定 `0xAA 0x55` |
| CMD | 1 | 命令字 |
| LEN | 1 | DATA 段长度，不含帧头、命令字、CRC 与帧尾 |
| DATA | LEN | 载荷 |
| CRC | 2 | CRC16-MODBUS（多项式 0x8005 反射形式 0xA001，初值 0xFFFF），低字节在前，覆盖范围从 CMD 到 DATA 末尾 |
| 帧尾 | 2 | 固定 `0x55 0xAA` |

固定开销 8 字节，单帧载荷上限 64 字节。

环境帧（CMD = 0x01，LEN = 0x0C，整帧 20 字节）：

| 偏移 | 长度 | 字段 | 换算 |
|---|---|---|---|
| 2 | 1 | CMD = 0x01 | |
| 3 | 1 | LEN = 0x0C | |
| 4 | 2 | 温度 | `int16`，实际值 = 原始值 / 100，单位 ℃ |
| 6 | 2 | 湿度 | `int16`，实际值 = 原始值 / 100，单位 %RH，负值表示传感器无效 |
| 8 | 2 | 气压 | `int16`，实际值 = 原始值 / 10，单位 hPa |
| 10 | 2 | 光照 | `uint16`，单位 lx |
| 12 | 2 | TVOC | `uint16`，单位 ppb |
| 14 | 2 | MQ135 | `uint16`，ADC 原始值 0~4095 |
| 16 | 2 | CRC | |
| 18 | 2 | 帧尾 | |

多字节字段一律大端（高字节在前）。

历史帧（CMD = 0x15，LEN = 24）整帧 32 字节，数据段的前 4 字节是原始时间戳，后 20 字节是板1 原始环境帧，板2 不做二次换算（`B2\FWLIB\inc\sys_frame.h:108,114-116`）。

### 3.2 命令字分区

| 区间 | 用途 |
|---|---|
| 0x01 | 板1 上报：环境帧（`sys_frame.h:79`） |
| 0x00、0x02~0x0F | 未分配。协议头只约定 0x10~0x7F 为下行请求（`sys_frame.h:94`），这一段没有定义，留作后续上报类命令 |
| 0x10~0x7F | 下行请求类（当前用到 0x10~0x14 与 0x16），另含板2 主动上报的历史帧 0x15 |
| 0x80~0xFF | 应答类，应答命令字 = 请求命令字 \| 0x80（`sys_frame.h:99`） |

### 3.3 下行控制命令

| CMD | 名称 | 请求 DATA | 应答 DATA |
|---|---|---|---|
| 0x10 | 设置转发开关 | 1 字节：0 关 / 1 开 | `[状态][新值]` |
| 0x11 | 设置缓存开关 | 1 字节：0 关 / 1 开 | `[状态][新值]` |
| 0x12 | 查询状态 | 无 | 见下 16 字节 |
| 0x13 | 清空缓存 | 无 | `[状态][清后条数 2 字节]` |
| 0x14 | 重启板2 | 无 | `[状态]` |
| 0x15 | 历史帧（板2 → 上位机） | 无（板2 主动上报） | 24 字节：4 字节原始时间戳（大端）+ 20 字节原始环境帧 |
| 0x16 | 触发或停止补传 | 1 字节：0 停止 / 1 开始（LEN = 0 视为开始） | `[状态][已补传低][已补传高][剩余低]`，应答命令字 0x96，共 4 字节 |

状态码：0 = 成功，1 = 参数错，2 = 不支持的命令，3 = 忙（当前实现中清缓存失败时返回）。

0x96 应答的 4 字节里，第 1 字节是补传状态（0 空闲 / 1 补传中 / 2 完成 / 3 出错，取值非法时也落在 3，`B2\FWLIB\inc\sys_frame.h:135-138`、`B2\main.c:1417`），第 2、3 字节是本次已补传条数的低字节与高字节，第 4 字节是剩余条数的低字节（`B2\main.c:723-726`）。

查询应答 16 字节：

| 偏移 | 长度 | 内容 |
|---|---|---|
| 0 | 1 | 状态码 |
| 1 | 1 | 转发开关当前值 |
| 2 | 1 | 缓存开关当前值 |
| 3 | 1 | 保留 |
| 4 | 2 | 收到并校验通过的帧数 |
| 6 | 2 | 校验失败的帧数 |
| 8 | 2 | 缓存中的记录条数 |
| 10 | 2 | 缓存丢弃计数 |
| 12 | 4 | 上电运行秒数 |

设计约定：

- 应答没有事务号，所以上位机同一时刻只允许一条在途命令（见第 6.5 节）。
- 重启命令先回应答、等发送完成后延时 100 ms 再复位，避免应答还没发完就断电。
- 未知命令回状态码 2，不静默忽略。

板1 的职责边界：采集、换算、显示、上报。它不做告警判定，也不写历史。

### 4.2 采集链路现状

`B1\main.c:741` 的实参是 `frame_build(f, m.temp_c, m.humi_rh, 0.0f, 0U, 0U, 0U)`，即**当前只有温湿度是实测值**，气压、光照、TVOC、MQ135 四项固定填 0。`SYS_BMP280_*`、`SYS_BH1750_*`、`SYS_CCS811_*`、`SYS_OLED_*` 这些驱动在 `main.c` 中出现 0 次，属于已写好但尚未接入采集链路的模块。组装测试时如果看到气压 0.0 hPa、光照 0 lx、TVOC 0 ppb，属于当前实现的预期现象，不是接错线。

### 4.3 喂狗方式

板1 的三个业务任务各自在自己的循环里报到，id 为 0/1/2（`B1\main.c:720,758,791`）。监控任务不占报到位，只调 `SYS_WDG_HeartbeatPoll()` 汇总（`B1\main.c:917`）。原先监控任务用 `SYS_WDG_Heartbeat(APP_TASK_COUNT - 1U)`，该值与第三个业务任务同为 2，两个任务撞同一格，第三个任务卡死也不会掉位，因此已改成只调 Poll（`B1\main.c:912-915` 的注释记了这件事）。

库里的 `SYS_WDG_HEARTBEAT_COUNT` 保持 0（`B1\FWLIB\inc\sys_wdg.h:45`）。该配置下 `SYS_WDG_Heartbeat()` 退化为 `(void)id`、`SYS_WDG_HeartbeatPending()` 恒返回 0、`SYS_WDG_HeartbeatPoll()` 直接喂狗并恒返回 1（`FWLIB\src\sys_wdg.c:167-219`），所以"上报是否齐全"这一判断当前不触发复位，报到与提示只是为该宏改成非 0 时预留。

## 5. 板2 数据通信端程序结构

板2 的三条数据通路：

1. 接收通路：LoRa 收帧 → 逐条校验长度、帧头、帧尾、命令字与长度字段、CRC16 → 队列。
2. 转发通路：队列取帧 → 写 Flash 缓存 → 通过 USART2 发给上位机。
3. 控制通路：USART2 接收中断收字节 → 命令分发 → 应答，用互斥量保证与转发通路不同时占用 USART2 的发送。
4. 补传通路：命令 `0x16` 启动 → 从最老一条开始读 Flash → 按原始时间戳经 USART2 补报 `0x15` 历史帧 → 用 `0x96` 回报进度，走完清空缓存（见 5.3）。

### 5.1 任务与队列

| 任务 | 栈 | 优先级 | 触发方式 | 职责 | 位置 |
|---|---|---|---|---|---|
| `vTaskLoraRx` | 512 字 | 3 | 20 ms 轮询 | 收 LoRa 数据、逐条校验、入队 | `S_N_sys\Project_2_数据通信端\Project\main.c:950` |
| `vTaskForward` | 512 字 | 4 | 阻塞等待队列 | 取时间戳、写 Flash 缓存、经 USART2 转发 | `main.c:988` |
| `vTaskCmdRx` | 512 字 | 3 | 20 ms 轮询 | 收上位机命令、执行、应答 | `main.c:1323` |
| `vTaskReplay` | 256 字 | 3 | 每 50 ms 一条 | 补传缓存里的历史帧（`0x15`），并回报 `0x96` 进度 | `main.c:1091` |
| `vTaskMonitor` | 256 字 | 5 | 1000 ms 周期 | 打印统计、喂狗、任务报到汇总 | `main.c:1482` |

`s_q_frame = xQueueCreate(4, FRAME_TOTAL)`（深度 4，每项 20 字节，`main.c:1639`）；`s_qt_tx_mtx = xSemaphoreCreateMutex()`（`main.c:1660`）保护 USART2 发送。补传任务通过 `replay_start()` / `replay_stop()` 与命令任务交互，两者共用同一把发送互斥量。

LoRa 收帧的校验顺序（`main.c:929` 起的 `frame_parse`）：长度必须等于 20；帧头 `AA 55`；帧尾 `55 AA`；命令字 0x01 且长度字段 0x0C；最后用 `MODBUS_CRC16(&f[2], 16U) != 0` 判断整段自洽（`main.c:932-940`）。任一不符即丢弃并计入坏帧。

### 5.2 接收中断的开启方式

`main()` 里对 Qt 串口用的是 `SYS_USART_InitRxIT(USART_QT, USART_QT_BAUD)`，不是只发送的 `SYS_USART_Init`。USART2 的中断服务函数在 `FWLIB\src\sys_usart.c` 里是 `__weak` 定义，工程内没有同名强定义，因此库版 ISR 生效，收到字节进环形缓冲，由 `SYS_FRAME_Poll` 取走喂给帧状态机。

### 5.3 断网缓存的结构与提交顺序

缓存位于 W25QXX（板载 GD25Q128），划分 16 个扇区共 64 KB，每扇区 128 槽、每槽 32 字节，合计 2048 条（`B2\FWLIB\inc\w25qxx_log.h:33-46`）。槽内布局是序号 4 字节、时间戳 4 字节、数据长度 2 字节、CRC16 2 字节，随后是 20 字节帧数据，没有独立的状态字。

写入顺序为"先写 `[4..32)` 的数据与 CRC，最后单独写 `[0..4)` 的序号"。序号是提交标志：空槽的序号字段为 `0xFFFFFFFF`（`B2\FWLIB\inc\w25qxx_log.h:46`），初始化扫描时序号非法的槽一律按空槽跳过，所以写数据期间掉电不会把残数据当成有效记录补传。

槽的推进是环形的，写指针按 `s_head = (s_head + 1) % total` 前进（`B2\FWLIB\src\w25qxx_log.c:342-343`），容量上限由 `W25QXX_LogCapacity()` 返回。读写与擦除都在 `W25QXX_LOG_LOCK()` 保护下进行，该宏在 FreeRTOS 下是 `vTaskSuspendAll()`，解锁是 `xTaskResumeAll()`（`w25qxx_log.c:75-76`）。锁内含页编程与整扇区擦除：单条写入约 1 ms，整扇区擦除最坏约 50 ms，清空 16 个扇区约 0.5~1 s，这段时间调度器被挂起。

擦除粒度是扇区。同一个扇区内还有未补传的记录时，不能为了腾一个槽就擦整个扇区；当前实现是在擦除后扣减有效条数并把被连带丢弃的条数累加到一个只增的丢失计数里（`w25qxx_log.c:306-307`），由查询命令的 `QA_LOST` 字段上报，使丢数据这件事可见而不是静默发生。

上电时 `W25QXX_LogInit()`（`w25qxx_log.c:176`）顺序扫描全部槽位恢复写指针、序号与有效条数（扫描循环在 `:199`），半截槽按空槽跳过。这段扫描对应板2 启动自检的第 07 项（`B2\main.c:344`）。

**补传通路**：`vTaskReplay`（`B2\main.c:1091-1161`）每 50 ms 读一条并组 `0x15` 历史帧发给上位机，从最老记录开始推进。读取时 `W25QXX_LOG_ERR_EMPTY` 与 `W25QXX_LOG_ERR_CORRUPT` 只跳过并计数，扫到范围末尾才收尾（`B2\main.c:1139,1145`）。收尾先清空缓存再上报完成（`B2\main.c:1063,1078-1084`），这样下次补传不会重发同一批数据。补传期间新到帧只计数不补发：`replay_start()` 把 `s_cache_on` 置 0 暂停写入，转发任务按 `s_replay_st` 判断并丢弃这些帧（`B2\main.c:739,1012-1019`）。上位机用 `0x16` 启停，进度靠 `0x96` 回报。

### 5.4 两个 `main.c` 的关系

两份 `main.c` 都同时包含板1 与板2 两套代码，用 `#if (SYS_TEST_BOARD == 1)` / `#else` 分开，实际编译哪一套由 Keil 工程的宏决定。两者已经分叉：板2 的 `main.c` 有 `vTaskCmdRx`（控制通道）、`vTaskReplay`（缓存补传）与 `APP_TASK_COUNT 3`，板1 的 `main.c` 里板2 分支停留在旧版（缺这两个任务）。为避免误用，板1 的 `main.c` 已把板2 分支改成 `#error`：把板1 工程的宏写成 `SYS_TEST_BOARD=2` 会在编译期直接报错，提示改用 `S_N_sys\Project_2_数据通信端\Project\main.c`。

因此"在模板上新建 `main.c`"的正确做法是：连同改过的 `FWLIB`、`FreeRTOS\port\FreeRTOSConfig.h`、`RTE\Device\STM32F407ZE\system_stm32f4xx.c` 一起复制，并在 Keil 工程的 C/C++ 宏里补上 `SYS_TEST_BOARD=1` 或 `2`；只换 `main.c` 会缺少帧层与驱动层的实现。

### 6.2 接收状态机

按字节喂入，逐字节匹配帧头 `AA 55`，依次校验长度合法性、CRC16、帧尾 `55 AA`。校验失败的字节不丢弃，而是回退重找帧头，避免一帧错误吃掉下一帧的开头。

解析成功后按命令字分流：`0x01` 且长度足够进环境帧通道；`0x15` 且长度为 24 进历史帧通道（`frameparser.cpp:335-341`）；带 bit7 的命令字进应答帧通道；其余计入"其他命令"统计。

### 6.3 告警判定

每项阈值分下限与上限，各有一个启用开关，另有回差。进入条件为"超过上限"或"低于下限"，恢复条件为"回到阈值 ∓ 回差 以内"。加回差的原因：测量值在阈值附近抖动时，不做迟滞会反复产生进入与恢复两条记录。补传回来的历史帧不参与告警判定。

### 6.4 配置落盘

阈值、告警总开关、曲线勾选、Y 轴自动量程、量程校验开关、串口与波特率写入 `上位机配置.ini`（与可执行文件同目录），启动时读回。界面上改动阈值后点确定即生效并落盘。

### 6.5 下行控制

`DevCtl` 维护一个命令队列，同一时刻只发一条，等应答。600 ms 无应答则重发，最多 3 次，仍无应答则报失败并放行下一条。超时值与重发次数按板2 命令任务 20 ms 轮询、正常往返小于 50 ms 估算，600 ms 约 10 倍余量，同时避免板2 未接时久等（`devctl.h:9-15`）。

设备状态回显到勾选框时用信号阻断，避免"回显状态"被当成"用户操作"而回发命令造成循环。

补传用 `DevCtl::startReplay()` / `stopReplay()`（`devctl.h:75-77`）下发 `0x16`，与其它下行命令共用同一套超时与重发；`0x96` 应答由 `handleReplayAck()` 解析成补传进度快照（`devctl.cpp:223-227`），界面据此刷新状态行。

破坏性操作（清空缓存、重启板2）二次确认。

## 7. 数据边界与量程约定

三层边界，各自负责不同的事：

1. 传感器层：读不到或读数越界时，按"无效"处理（例如湿度用负值表示无效），而不是报一个看起来正常的数。
2. 协议层：字段用定点整数（温度湿度 ×100、气压 ×10），CRC 保证传输完整性；帧长度与 CRC 不符即丢弃。
3. 应用层（上位机）：每个物理量有合理量程（温度 −40~80 ℃、湿度 0~100 %RH、气压 300~1100 hPa、光照 0~20000 lx、TVOC 0~5000 ppb、MQ135 0~4095）。超出量程的值仍然显示并写入 CSV（状态列标 `+RANGE`），但不参与告警判定，避免上游没接传感器时的默认值刷出假告警。
4. 补传数据：`0x15` 历史帧入库时按原始时间戳插进曲线（`SerialMonitor\datamodel.cpp:212` 的 `addHistory()`），不写入实时统计、不参与告警判定，并按"原始时间戳 + 20 字节原帧"去重（`SerialMonitor\datamodel.h:132-136`）。CSV 现为 10 列，末列"数据来源"取 `实时` 或 `补传`，表头由 `SerialMonitor\datamodel.cpp:311-313` 的 `CsvRecorder::header()` 单点生成（`Qt上位机设计.md:164` 已是 10 列）。

可调项：六项阈值与其启用开关、回差、Y 轴是否自动量程、量程校验开关、曲线勾选，均在界面上可改并落盘；固件侧的换算系数在 `sys_frame.h` 里是 `#define` 编译期常量（`sys_frame.h:65-73`），没有运行期配置接口，改动需要重编固件（原因：定点换算在采集侧完成，运行期改变换公式会引入整数溢出与量纲混乱的风险）。

## 8. 组装与联调步骤

### 8.1 接线与跳线

板1：

1. 调试口接 PC：USART1（PA9/PA10）经板载 CH340C。若用外接 USB-TTL，则是 PA9↔模块 RXD、PA10↔模块 TXD，115200 8N1。
2. DHT11：数据脚 PG9，数据线对 3.3 V 接 4.7 kΩ 上拉（`sys_dht11.h:44-45` 要求）。
3. LoRa E22：模块 TXD → MCU PB11（USART3_RX），模块 RXD → MCU PB10（USART3_TX），M0=PB0、M1=PB1、AUX=PB2，串口 9600 8N1。两块模块的频段、地址、网络 ID、信道、空中速率必须一致。

板2：

4. 调试口接 PC：USART1（PA9/PA10），板上有 CH340C，但需要插两枚跳线帽（PA9T↔URXD、PA10R↔UTXD），不插跳线调试口没有输出。
5. 上位机串口：PA2/PA3 经跳线 **P6** 选 SP3485（RS485）或 SP3232（RS232），**二者只能选一个**。用 USB-TTL 或 DB9 接 PC 时把 P6 跳到 SP3232 侧，115200 8N1。
6. LoRa E22：USART6（PC6/PC7），从 P1 双排排针引出，M0/M1/AUX = PE5/PE6/PE7，9600 8N1。
7. ESP8266：USART3（PB10/PB11），经跳线 P10 接 ESP8266 模块或 3P 端子。
8. W25Q128：SPI1（PB3=SCK / PB4=MISO / PB5=MOSI），片选 PB14（软件片选）。NRF24L01 共用 SPI1，片选 PG7；RS485 的方向脚 PG8 与 NRF24L01 的中断脚同脚。因此**要同时用 Flash 缓存与 RS485，必须把 NRF24L01 模块拆下**。
9. 模拟跳线 J8：PA5/PA4 上有 `R_ADC / STM_ADC / P_TOUCH / STM_DAC / TAD1` 多路信号。量 DAC 输出前先确认 J8 短接到 `STM_DAC`；用触摸前先短接 `P_TOUCH ↔ STM_ADC`。
10. CAN：PA11/PA12 同时是 USB OTG 的 D−/D+，要用 CAN 必须把 P9 跳线跳到 CAN 侧。
11. 上位机跳线编号已统一为 **P6**：`B2\FWLIB\inc\lora_e22.h:49,92` 与 `B2\FWLIB\inc\sys_usart.h:13,24` 原写成 P5，已按 `B2\README.md:178,783,2402` 与原理图改为 P6。原理图依据（`普中-天马 F407开发板原理图.pdf`）：P6 是 6 针座，网络名为 `USART2_TX / USART2_RX / RS485_RX / RS485_TX / R_ADC / VCC3.3`，即 PA2/PA3 到 SP3485 或 SP3232 的二选一跳线；板2 的 P5 是 18 针扩展排针（`DS18B20 / DCMI_* / STM_DAC / USART3_TX,RX / MPU_INT` 等），与串口跳线无关。

### 8.2 上电顺序与预期现象

1. 只插板1，接调试串口，看启动自检输出，全部项目应通过。
2. 只插板2，接调试串口，看启动自检输出，全部项目应通过。
3. 板1 与板2 之间的 LoRa 参数（频段、地址、速率、信道）必须一致，两块模块的天线接好后再上电。
4. 板2 的 USART2 接 USB-TTL（或经 RS232 收发器接 DB9）连 PC，打开上位机对应串口，波特率 115200 8N1。
5. 上位机应开始收到帧：卡片数值刷新、曲线出现、统计里"成帧"计数递增。
6. 点"查询板2 状态"，应回一行应答，状态下显示转发开关、缓存开关、缓存条数、运行秒数。

### 8.3 故障定位对照

| 现象 | 先查 | 再查 |
|---|---|---|
| 上位机一个字节都没收到 | 板2 是否在跑（调试口有没有监控打印） | 跳线是否在 RS232 侧、TX/RX 是否交叉、波特率 |
| 收到字节但不成帧 | 波特率偏差 | 统计里的 CRC 错、长度错、帧尾错三项哪个在涨 |
| 成帧计数在涨但卡片不动 | 命令字是否为 0x01 | 帧长度是否符合 20 字节 |
| 曲线断断续续 | LoRa 信号与地址/信道 | 板2 缓存与转发的开关是否被关掉 |
| 下发命令无应答 | 串口是否以读写方式打开 | 板2 命令任务是否在跑、应答统计是否递增 |
| 告警不触发 | 阈值启用开关 | 数值是否被判为超量程（统计里有"量程可疑"计数） |

### 8.4 验收要留的证据

- 两块板的启动自检输出（截图或文本）。
- 上位机四个自检命令的退出码与报告文件。
- 上位机界面截图、CSV 记录片段。
- 控制命令下发的应答记录（十六进制收发对照）。

风险提示：

- 板2 的 W25QXX 与 NRF24L01 共用 SPI1，RS485 的方向脚与 NRF24L01 中断脚共用 PG8。要同时用缓存与 RS485，需要拆掉 NRF24L01 模块。
