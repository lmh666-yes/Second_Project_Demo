## 1. 项目做什么

用两块 STM32F407 组成"无线采集 + 边缘网关"的分布式系统，对实验室的温湿度、气压、光照、空气质量做长期监测，数据同时送到电脑上位机和云端，超限时本地与远程双重告警。

数据通路：采集节点通过 I2C 挂 SHT30、BMP280、BH1750、CCS811 四类传感器，1 秒一轮采集，经滑动滤波后按自定义的 20 字节二进制协议组帧、带 CRC16 校验，通过 LoRa 无线发出。

网关端也是 F407，用串口 DMA + 空闲中断收帧，状态机解析并校验，然后同时走两路：一路通过 RS232 发给 Qt 上位机做实时曲线和 CSV 记录，一路通过 ESP8266 走 MQTT 上巴法云，云端可直接推到手机。网关侧还有 W25Q128 断网缓存：云端断开时把数据落进 Flash，网络恢复后按序号补传。上位机用 Qt 写，实时显示 6 个参数、画历史曲线、导出 CSV，带双阈值迟滞告警和协议一致性自检。

## 2. 技术栈总览

| 层次 | 技术 | 说明 |
|---|---|---|
| 硬件 | STM32F407ZET6（采集节点）+ STM32F407ZGT6（边缘网关） | 双 F407，同系列不同 Flash 容量（512 KB / 1 MB） |
| 底层驱动 | ST 标准外设库（StdPeriph Library） | 非 HAL；两板工程各含 40+ 个自研 `sys_*` 封装驱动 |
| RTOS | FreeRTOS 10.4.6（原生 API，非 CMSIS-RTOS 封装） | heap_4，30 KB 堆，抢占式调度 |
| 无线 | LoRa E22-400T22S（433 MHz） | 板1 ↔ 板2 的唯一链路 |
| 云端 | ESP8266 + AT 指令 + MQTT（巴法云 bemfa.com） | 通过 WiFi 上云，可直接推微信/小程序 |
| 上位机 | Qt 6.11.2（MinGW 64-bit）+ QCustomPlot | 串口通信、实时曲线、CSV、告警 |
| 传感器 | SHT30(I2C) / BMP280(I2C) / BH1750(I2C) / CCS811(I2C) / MQ-135(ADC) | 4 类物理量 + 2 类空气质量 |
| 存储 | W25Q128 SPI Flash（板载） | 断网缓存，64 KB 专用区 ≈ 2000 条 |
| 协议 | 自定义 20 字节二进制帧 + CRC16-MODBUS | 三端（板1/板2/Qt）一致 |

### 3.2 任务划分与优先级

板1（采集节点）

| 任务 | 优先级 | 周期/触发 | 职责 |
|---|---|---|---|
| SensorTask | 3 | 1 s（vTaskDelayUntil） | 读 5 路传感器，失败填故障标记不阻塞 |
| ProcessTask | 3 | Queue1 触发 | 滑动/中值滤波、双阈值判断、按协议打包 |
| CommTask | 4 | Queue2 触发 | 组帧 + CRC16 + 经 USART3 发 LoRa |
| MonitorTask | 5 | 定时 | 心跳位图巡查，全刷新过才喂 IWDG |

板2（边缘网关）

| 任务 | 优先级 | 周期/触发 | 职责 |
|---|---|---|---|
| CommRxTask | 4 | Sem1（空闲中断） | 状态机解帧、CRC 校验、提取数据 |
| ForwardTask | 3 | Queue3 触发 | 经 USART2 透传给 Qt 上位机 |
| CloudTask | 3 | 30 s / 告警插播 | AT 指令 + MQTT 上报巴法云 |
| CacheTask | 3 | Queue4 触发 | 断网写 W25Q128，恢复后按序号补传 |
| MonitorTask | 5 | 定时 | 心跳位图 + 喂狗 + ESP8266 在线巡查 |

> CloudTask 与 ForwardTask 必须分开：AT 指令是一问一答，单条 `AT+CIPSEND` 可能阻塞几百毫秒。
> 如果和 Qt 转发挤在一个任务里，云端阻塞时会连带阻塞上位机的实时曲线。

### 6.2 可直接复用的模块

这些模块正好覆盖本项目最花时间的部分：

| 模块 | 位置 | 对本项目的价值 |
|---|---|---|
| `sys_frame` | 两板都有 | 组帧/收帧状态机：内建帧同步（帧头不对自动丢到下一个）、粘包/半包处理、校验错自动重找帧头、`SYS_FRAME_Verify()` 双保险、`SYS_FRAME_ErrCount()` 链路质量统计。2026-10-10 已完成改造：帧格式为定稿的 `AA 55 \| CMD \| LEN \| DATA \| CRC16(低字节在前) \| 55 AA`（总长 `8+LEN`，CRC 范围 = 帧内 `[2 .. 4+LEN)`），旧的单字节头/尾与"简化帧"（`SYS_FRAME_WITH_LEN`）已删除，并新增 `SYS_FRAME_BuildEnv()` / `SYS_FRAME_UnpackEnv()` 两个环境帧助手 |

| `MODBUS_CRC16()` | 板2 `modbus.h:110` | 同上（板2 版本，注释明确 `frame[6]=c&0xFF, frame[7]=c>>8` 低字节在前） |

| `SYS_WDG_ResetCauseDecode()` | `sys_wdg.h:130` | 可判断复位原因（`SYS_WDG_RST_IWDG` 独立看门狗复位 / `RST_WWDG` / `RST_POR` / `RST_BOR` 等），能做复位原因诊断 |
| `sys_fault` | 两板 `sys_fault.h` | CPU 故障记录：接管 NMI/HardFault/MemManage/BusFault/UsageFault，把出错地址、寄存器、故障状态存进全局 `SYS_FAULT_Record`，可 `SYS_FAULT_Report()` 生成文字发串口。与 FreeRTOS 共存（不碰 SVC/PendSV/SysTick） |

| `w25qxx` + `w25qxx_log` | 板2 | W25Q128 驱动 + 日志封装，断网缓存底座现成 |

## 7. 关键工程决策

| 决策 | 选择 | 理由 |
|---|---|---|
| 协议精度 | 温度/湿度 ×100，气压 ×10 | SHT30 分辨率 0.01 ℃，用 ×10 只有 0.1 ℃ 分辨率，浪费传感器精度；气压若用 ×100，1013.25×100 = 101325 超出 uint16 上限 65535，所以只能 ×10 |
| CRC 字节序 | 数据段大端，CRC 低字节在前 | 大端便于人工阅读抓包；CRC16-MODBUS 的标准传输顺序本来就是低字节在前，跟随标准比自创更不易出错 |
| 解帧策略 | 校验失败丢一个字节重新找帧头 | 若跳过整帧长度，遇到帧尾 `55 AA` 与下一帧头 `AA 55` 粘连成 `55 AA AA 55` 时会连续丢帧 |
| 缓冲环设计 | 环形缓冲 + 状态机 | 串口是字节流，可能收到半个包或三个包，不能用"一次读到一包"的假设 |
| 云端报文格式 | `#` 分隔文本（不是 JSON） | 巴法云可直接把消息推微信/小程序，文本格式在手机上可直接阅读；JSON 需要额外一层解析，演示中没有收益 |
| 断网缓存位置 | 网关侧 W25Q128，不是采集端 | 采集端加 Flash 会增加功耗与成本；网关常供电，且工程里 `w25qxx_log.c` 现成，零采购零硬件改动 |
| 中断优先级 | 串口 ISR 抢占优先级必须 ≥ 5 | `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`，优先级数值小于 5 的中断里不能调 FreeRTOS API，否则破坏内核临界区 |
| 喂狗方式 | 心跳位图，全任务刷新过才喂 | 若只看"MonitorTask 自己还在跑"，某个业务任务死循环时狗照样被喂，故障被掩盖 |
| 光照传感器 | BH1750（I2C）而非光敏电阻 + ADC | 光敏电阻需要标定才能得到 lux，且温漂大；BH1750 直接出数字照度，省掉标定环节 |
| 是否用 HAL | 不换，继续标准库 | 见第 9 节 |

## 9. 关于是否改成 HAL + STM32CubeMX

`方案13.md` 里有一条建议是"改为纯 HAL 库 + STM32CubeMX"。结论是不换，理由如下。

| 维度 | 继续用标准库（现状） | 改成 HAL + CubeMX |
|---|---|---|
| 已有代码 | 两板各 40+ 个 `sys_*` 驱动 + 完整的 `FWLIB`，全部可用 | 全部作废重写，等于把项目推倒重来 |
| 外设驱动经验 | 需要理解寄存器时序（I2C 的 IDLE 标志、DMA 请求映射、时钟总线） | CubeMX 生成代码，难以说明生成代码的内部行为 |
| 工作量的时间成本 | 7 个传感器驱动 + 业务逻辑 | 上述 + 重新移植 FreeRTOS + 重写全部底层 |
| 对本项目的收益 | — | 几乎为零（本项目的外设在标准库下都有驱动） |
| 对代码掌握程度的体现 | 读参考手册后自己封装底层驱动库 | 使用工具生成 |

折中方案：

- 主线继续用标准库
- 同时读懂 HAL 的对应写法（`HAL_I2C_Master_Transmit`、`HAL_UART_Receive_DMA` 等），能说清标准库和 HAL 的差异与适用场景
- 如果将来投偏应用/快速开发的岗位，可以在另一个小 demo 里用 CubeMX 走一遍，但不要动这个项目

> 本机已装 `E:\STM32CudeMax\STM32CubeMX.exe`、`E:\ST32 Cude IDE\STM32CubeIDE_2.0.0`，
> 需要做 HAL 对比 demo 时工具是现成的。

## 11. 技术问题与回答要点

| 问题 | 要点 |
|---|---|
| 为什么用 LoRa 不用 WiFi/蓝牙 | LoRa 是 Sub-1GHz 窄带，穿透和绕射能力比 2.4 G 强，传输距离远（开阔地几公里）且功耗低；本项目是固定式低速采集（1 s 一帧 20 字节），不需要 WiFi 的带宽。WiFi 放在网关端做上云，分工是"LoRa 负责可靠到达，WiFi 负责接入互联网" |
| 为什么用两块板而不是一块 | 采集节点要放到被测环境里（可能离实验室角落很远），网关要靠近路由器和电脑，物理位置分开就需要无线链路；双板也天然形成分布式架构，网关能做缓存、协议转换、多节点汇聚 |
| CRC16 怎么算的 | 多项式 `0xA001`（MODBUS），初值 `0xFFFF`，逐字节异或后右移 8 次，每次最低位为 1 就异或多项式；低字节先发 |
| 帧尾和下一帧帧头粘在一起怎么办 | 解析器以帧头为最高优先级：每次同步失败或 CRC 失败都只丢一个字节重新找 `AA 55`，同时要求"长度字段 = 0x0C"和"帧尾 = 55 AA"双重确认。测试里有专门构造 `...55 AA AA 55...` 的用例 |
| 中断里为什么不能随便调 FreeRTOS API | FreeRTOS 用 `BASEPRI` 屏蔽中断来保护临界区。抢占优先级数值小于 `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY`（本工程=5）的中断不受内核控制，在这种中断里调 `xQueueSend` 之类可能破坏内核数据结构，所以必须用 `FromISR` 版本且优先级 ≥ 5 |
| 看门狗为什么不用简单喂狗 | 简单喂狗只能检测"整个系统死了"。用心跳位图：每个任务完成一轮工作后置自己的位，MonitorTask 检查全部位是否都被刷新过才喂狗，这样单个任务死循环也能被发现。事件驱动的任务还配了软定时器兜底 |
| 堆只有 30 KB 够用吗 | 任务是动态创建的，队列、信号量、任务栈都从这 30 KB 出。实测记录 `xPortGetFreeHeapSize()`，保留 >8 KB 余量；`configCHECK_FOR_STACK_OVERFLOW = 2` 和 `vApplicationMallocFailedHook` 都开了，异常时会打印任务名并停机，便于定位 |
| 断网了数据怎么办 | 网关 CacheTask 把帧写进 W25Q128 的 64 KB 专用区，每条 18 字节按 32 字节对齐，约 2000 条 ≈ 16 小时；每条自带序号和 CRC16；网络恢复后按序号升序、约 1 s 一条补传直到追平，不丢也不重 |
| 最难的地方 | 串口空闲中断 + DMA 收不定长帧，以及 I2C 上挂多个传感器时的地址冲突与总线锁死处理。具体表现：上电先 `SYS_I2C_Scan()` 逐个确认地址；多个模块的板上拉并联后等效阻值过小，要断开多余上拉 |
| 重做一次会怎么改 | 1) 一开始就把节点 ID 和状态位放进帧格式；2) 更早引入逻辑分析仪，I2C 调试会快很多；3) 传感器一次只挂一个，不全插上 |
| 为什么不用 MQTT 的 QoS 1/2 | 应用层已经用序号 + Flash 缓存 + 补传保证不丢，QoS 0 够用；QoS 1/2 会增加握手往返，在 ESP8266 的 AT 流程里实现复杂。可靠性放在应用层做，链路层保持简单 |
