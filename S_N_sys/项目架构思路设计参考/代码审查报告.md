   - **BMP280**（`0x76`/`0x77`）：8 位寄存器（`0xD0` chip id、`0xF4` ctrl_meas、`0xF7` 数据、`0x88..0x9F` 标定系数）→ 用 `SYS_I2C_ReadBytes` / `SYS_I2C_WriteByte`。
   - **CCS811**（`0x5A`/`0x5B`）：8 位寄存器（`0x00` STATUS、`0x02` 结果、`0x20` HW_ID、`0xF4` APP_START）→ 同上。它的 `APP_START(0xF4)` 是"**只发寄存器号、不带数据**"的写。**初稿这里给的做法（`SYS_I2C_WriteBytes(bus, addr, 0xF4, NULL, 0)`）是错的**：`i2c_writebytes_locked()` 开头就是 `if (p == 0 || buf == 0 || len == 0U) return SYS_I2C_ERR_PARAM;`，`NULL` 和 `len == 0` 都会被直接拒掉：一个"看着像成功、实际什么都没发"的静默失败。正确做法是**新加一个纯命令写原语** `SYS_I2C_WriteCmd(id, addr7, cmd)`。
   - **BH1750**（`0x23`/`0x5C`）：**没有寄存器号概念**，写进去的就是命令字节本身（`0x01` 上电、`0x10` 连续 H 分辨率、`0x20` 单次 H 分辨率…），读回来是 2 字节光照值。→ 命令用 `SYS_I2C_WriteCmd`；**但读回时现有 API 全都不适用**：`SYS_I2C_ReadBytes` 会先发一个"寄存器号"，而对 BH1750 来说那个字节**是命令**（`0x00` 就是 Power Down，器件会被静默关掉，现象是"能读到数但永远不变"）。⇒ 还需要 `SYS_I2C_ReadRaw(id, addr7, buf, len)`（不发寄存器号、直接 repeated-start 读）。这两个原语本项施工时已一并补进两板 `sys_i2c.c` / `sys_i2c.h`，并都走同一把总线锁。

#### S1 — 状态字永远不是 VALID，断网缓存 100% 读不出来，已修
- 位置：`Project_2_数据通信端\Project\FWLIB\src\w25qxx_log.c:222`（原行号）、配 `:243` 写、`:116` 读、`:170` LogInit
- 原代码：`log_put_u32(&rec[0], W25QXX_LOG_EMPTY);   /* 占位，等会儿才真正落下去 */`
- 故障链：全文件**只有这一处**给 `rec[0]` 赋值 → 第 ③ 步 `W25QXX_Write(&rec[4], addr+4, 60)` 落盘的数据段是对的，第 ④ 步 `W25QXX_Write(&rec[0], addr, 4)` 落盘的**状态字却是 0xFFFFFFFF** → 读端 `:116 if (st != W25QXX_LOG_VALID) return W25QXX_LOG_ERR_EMPTY;` 把**每一条记录**都判成空槽 → `:170` LogInit 数出 0 条。
- 后果：写入报成功、`W25QXX_LogCount()` 与补传任务看到的永远是 0 条。**项目核心卖点（断网缓存）整体不成立。**
- 修复（现 `w25qxx_log.c:288`）：
  ```c
  /* 先在 RAM 里填 VALID：真正落盘是第 ④ 步单独写 [0..4)，
   * 那一步成功这条记录才算数，之前这里误写成 EMPTY，
   * 导致状态字永远是 0xFFFFFFFF，读端 100% 判成空槽、功能整体失效 */
  log_put_u32(&rec[0], W25QXX_LOG_VALID);
  ```
- 复核：槽布局 = `[0..4)` 状态字 / `[4..8)` seq / `[8..12)` ts / `[12..14)` len / `[14..16)` sum / `[16..64)` 数据，`HDR_SIZE=16`、`SLOT_SIZE=64`、`PAYLOAD=48`、`EMPTY=0xFFFFFFFF`、`VALID=0x5A5A5A5A`（`w25qxx_log.h:78-79`）。**提交顺序 237→243（先写数据、最后写状态字）本身是对的，没动**——这是正确的原子提交设计。

**G1 的重要性**：抢占优先级 2 **数值上小于** 阈值 5，意味着该 ISR **不受内核临界区屏蔽**。按键驱动最自然的写法是在 EXTI 回调里 `xQueueSendFromISR`，一旦这么做就会触发 `configASSERT` 断言，**未开断言则静默损坏队列数据**。已改的 11 处（板1 `sys_usart.h`、`sys_tim.h`、`sys_dma.h`、`sys_exti.h`、`sys_rtc.h`；板2 同 5 个 + `sys_can.h`）现全部为 5，已用 grep 全仓复核**零残留**。

**G2 为什么隐蔽**：FreeRTOS 靠 `BASEPRI` 屏蔽临界区，只有 `Group_4` 时抢占数值才与寄存器高 4 位一一对应。`Group_2` 会把 pre 编码到 bit[7:6]，让**越界优先级"看起来合法"**却仍然撕内核临界区。补充：旧注释里写的"库默认 Group_2"已过期，两板 `sys_nvic.h:59` 现为 `NVIC_PriorityGroup_4`。

**F1 的根因值得记一笔**：原先 `fx_state/fx_cmd/fx_chk/fx_idx/fx_dlen/fx_data/fx_ready/fx_rcmd/fx_rlen/fx_rbuf/fx_err` 全是**文件级 static 单例**，而 `SYS_FRAME_Poll(uart)` 把**任意串口**的字节喂进同一套状态机 → 板1（调试口 + LoRa）两个任务各自 Poll 时字节在同一 `fx_idx/fx_state` 上交错 → 帧截断/粘连/校验随机失败，**且难复现**；板2 四路必爆发。已改为 `typedef struct { ... } FrameRx_t;` + `static FrameRx_t fx[SYS_USART_COUNT];`，每个函数先取 `FrameRx_t *f = fx_get(uart);`。

**W1 为什么危险**：`sys_wdg.h:80-81` 的**官方用法注释**就是"主循环只留一句 `SYS_WDG_HeartbeatPoll()`"，而 `SYS_WDG_HEARTBEAT_COUNT` 默认 `0`，原代码在 `COUNT == 0` 分支直接 `return 0U;`（**不喂狗**）→ **照文档写就上电即复位循环**。修复选择改库而不是改每个 `main.c`：`COUNT == 0` 时退化为 `SYS_WDG_Feed(); return 1U;`，并在注释里把"模式甲（COUNT>0 死任务检测）/ 模式乙（COUNT=0 普通喂狗）"讲清楚。

### 3.5 滤波算法（板2）

38. 【已处理】 **`sys_filter.c` `FILTER_Median()` 会就地破坏调用方缓冲区** —— 已在其文档里写明"**返回后数组只是首部有序**，需要完整升序数组的算法不能复用本函数"；同时 `FILTER_TrimmedMean` 不再复用这个半程排序（见第 39 条）。

41. 【已处理】 **`FILTER_LpfInit` 的 α 是一阶近似**：已改为离散精确式 **`a = 1.0f - expf(-2π·fc/fs)`**（由 `f_c = (fs/2π)·ln(1/(1-α))` 反解），并新增"截止频率到奈奎斯特以上时 a = 1.0f"的明确分支。近似式只在 `fc << fs` 成立，而"fc 相对 fs 有几个百分点"正是本项目最常遇到的场合：**fs=1kHz 滤到 50Hz 时精确 α≈0.270、近似 α≈0.314，实际截止频率高了约 16%**，做滤波算法对比实验时截止频率对不上就没法比较。非法参数回落的魔法数 `0.2f` 保留但已加注释说明。
42. 【已处理】 **`FILTER_LpfUpdate` 与 `KALMAN_Update` 无 NaN/Inf 防护**：两者都加了文件私有的 `*_is_finite()`（手写比较，不依赖 `<math.h>`）。**核心机理**：两者都是带记忆的递推，只要有**一拍** NaN/Inf 就**永远**出不来，且往后再喂多少正常值都救不回来；卡尔曼更阴：**参数**里混进 NaN 也致命，因为 `if (q <= 0.0f)` 对 NaN 是**假**，`KALMAN_Init(&kf, NAN, 4.0f)` 会返回 `KALMAN_OK`，然后 `(p+r) <= 0.0f` 也是假 → `k = NaN` → 两个钳位（`<0`/`>1`）同样都是假 → `x` 永久 NaN。坏样本一律**整拍丢弃、保持上次输出**（不按 0 计，会在曲线下冲段造成凹陷；也不用 0 重置，会扔掉已收敛状态）；`FILTER_LpfSetAlpha` 另加了 `!(alpha == alpha)` 判断（原两句钳位对 NaN 都判假，"钳位挡不住'不是数'"）。
43. 【已处理】 **`mqtt.c` `(int32_t)(f + 0.5f)` 对 NaN/Inf 无保护**：`MQTT_PublishFloat` 先判 `!(f == f)` 则返回 `MQTT_ERR_PARAM`（**NaN 拒发**：把坏值当 0 发出去，云端会显示成"温度 0 度"，比上报失败难查得多），再把超量程钳到 ±20 亿，最后才转整数（`(int32_t)NaN` / `(int32_t)1e30` 是未定义行为，ARM VCVT 输出随实现而定）。

## 8. 三条主要教训

1. **不要把"编译通过"当成"驱动能用"。** 审查当时两板 `main.c` 还是空骨架，链接器把所有驱动裁掉了 —— `0 Error / 0 Warning` 连同 `Program Size` 一起，都是**弱到近乎无信息量**的信号。**这条到现在依然成立，只是原因变了**：`main.c` 已经填成上千行的真程序（板1 1075 行、板2 1695 行，`Program Size` 因此有意义了），但死代码消除是**按函数**做的：实测板2 映像里 `MQTT_PublishFloat` 不在（`main.c` 没调它）、`modbus.c` 只留下 `MODBUS_CRC16`、`at24c02.c` 整体不在（补传做完后 `sys_frame.c` 的 `SYS_FRAME_BuildEnv` 被自检 08b 调用，已进映像）。要验证"某个改动真的被链接进去了"，只能查 `.o` 的符号表；要验证驱动正确，只能上板。
2. **`SYS_XXX_IRQ_PRE_PRIO` 这类"数值语义"的宏，光看数字看不出对错。** 2 和 5 都是合法的 NVIC 优先级，但 2 < `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY(5)` 的含义是"这个 ISR 不受内核屏蔽"，一旦在里面调 `*FromISR` 就会静默损坏内核数据结构。**上 FreeRTOS 后，所有中断优先级宏都必须和 `FreeRTOSConfig.h` 的阈值对着看。**
3. **本项目最容易重复出现的问题：往注释里写示例代码时不能出现 `/*` 或 `*/`。** AC5 会报 `#9-D: nested comment is not allowed`（板2 还会变成 `error #169: expected a declaration` + `Target not created`），后面带一串连锁错误（`#40 expected an identifier`、`#940-D missing return statement`），看起来像别处的毛病。**已经出现 5 次**：`sys_clock.h`、`sys_rtos.h`、`sys_adc.h`、`sys_dma.h`、`oled.c`，最后一次是 `w25qxx.h` 里给 `W25QXX_WriteSafe` 写的示例 `if (W25QXX_WriteSafe(...) == 4U) { /* 稍后再试 */ }`，这段示例正写在"说明本项目不能这么写"的那段注释里。**写示例一律用纯文字描述，不要照抄 C 的花括号块。**
   现在已有一个可复用的静态检查脚本（本报告的方法）：逐字符扫描 `FWLIB` 下所有 `.c/.h`，维护"代码 / 字符串 / 字符字面量 / 块注释"四态机，只找 `/*`、`*/` 与 `//`，报告未闭合或嵌套的位置。**实测 173 个文件全部通过**：改动后跑一遍，比等编译器报错快得多。注意写这个脚本时**块注释内部不能再把 `"` 当字符串起点**（第一版就是这么写的，结果报出 123 个假阳性）。

## 9. 引脚占用冲突核查（上板前必须确认）

**为什么单独列一章**：本轮修的是代码缺陷，但"两个模块把同一个引脚写进各自的 `#define`"这种问题，**编译器一个字都不会说** —— 两边都编得过，两边都会 `GPIO_Init` 那个脚，后 init 的把前一个悄悄改掉。`lora_e22.h` 的注释写着 M0/M1/AUX 是"查过原理图确认空闲"的默认值，但把两板 `FWLIB\inc` 下**所有** `#define X_PORT GPIOx` + `#define X_PIN GPIO_Pin_n` 配对枚举出来之后，情况并非如此。

### 9.1 板2（F407ZG）—— LoRa 默认脚位曾与三个模块重叠（已迁移到 PE5/PE6/PE7）

| 引脚 | 旧用途（已废弃） | 同脚上的其它模块 | 处置 |
|---|---|---|---|
| **PA4** | `SYS_LORA_M0`（推挽输出，驱动接管） | `sys_dac.h` 的 `SYS_DAC1`；`sys_adc.h` 的 `SYS_DAC_OUT` | 已迁到 **PE5** |
| **PA5** | `SYS_LORA_M1`（推挽输出，驱动接管） | `sys_dac.h` 的 `SYS_DAC2`（该模块 `SYS_DAC2_ENABLE 0`）；`sys_adc.h` 的 `SYS_ADC_JMP`；**`ntc_pt100.h` 的 `SENSOR_ADC`，而它 `SENSOR_ENABLE 1`（默认就是开的）** | 已迁到 **PE6** |
| PA6 | `SYS_LORA_AUX`（输入上拉） | 无 —— 板2 的 W25QXX 走 SPI1 **重映射**（PB3/PB4/PB5），所以 PA6 不再是 SPI1_MISO | 顺带迁到 **PE7**（与 M0/M1 同端口） |

- **为什么必须迁**：`PA4` / `PA5` 是 F407 硬件固定的 `DAC_OUT1` / `DAC_OUT2`。只要 `sys_dac` 一初始化，DAC 与 LoRa 的推挽 GPIO 会同时驱动同一个脚 —— 这不是"谁先谁后"的软件问题，是**电气争用**；而 `PA4`/`PA5` 在板2 原理图上还是模拟跳线 **J8 的公共端**（`README.md:177`）。
- **当时不是活冲突**：板2 `main.c` 只 `Init` 了 `SYS_NVIC` / `SYS_USART` / `LED` / `SYS_RTC` / `W25QXX` / `SYS_DHT11` / `LORA_E22` / `ESP8266` / `SYS_WDG`，**没有调** `SYS_DAC_Init()` / `sys_adc` 初始化 / NTC 初始化（`grep` 命中数均为 0），所以现状能跑，但那是"还没碰到"，不是"不会碰到"。
- 【已处理】 **2026-10-11 已按下面的建议迁移**：`SYS_LORA_M0/M1/AUX_PORT/PIN` 改成 **PE5 / PE6 / PE7**（板2 `FWLIB\inc\lora_e22.h:177-182`），`lora_e22.c` 一行都没动（这正是把脚位做成宏的用意）。依据：`README.md:2497` 记 PE5 为板上空闲脚、`README.md:2543` 记 PE6/PE7 空闲，再用 `python 本地工具\仓库巡检\pin_audit.py` 扫全库 `#define X_PORT`/`X_PIN` 配对，**PE5/PE6/PE7 在库内无人认领**（板1 的 PB0/PB1/PB2 同样干净，故未动）。
- 迁移后重跑 `python 本地工具\仓库巡检\pin_audit.py`（`_pin_audit.txt` 已刷新）：板2 **冲突引脚数仍是 15 处**：`PA4`/`PA5` 本来就与 LoRa 无关地互相抢（`PA4` = `SYS_DAC_OUT` vs `SYS_DAC1`；`PA5` = `SENSOR_ADC` vs `SYS_ADC_JMP` vs `SYS_DAC2`），所以剩下的是 §9.3 那些库内重叠。**真正变化的是归属**：`SYS_LORA_M0/M1` 从 `PA4`/`PA5` 的占用者清单里消失、`PA6` 从"被占用"退回"无人认领"、新增 `PE5`/`PE6`/`PE7` 三个占用者。三处计数：板2 头文件 58 / 占用 62 / 冲突 15 / 无人认领 50；板1 头文件 37 / 占用 45 / 冲突 7 / 无人认领 67。

### 9.2 板1（F407ZE）—— LoRa 脚位干净，但库内另有重叠

| 引脚 | 重叠情况 | 严重度 |
|---|---|---|
| **PB0 / PB1 / PB2** | 只有 `lora_e22.h` 的 `SYS_LORA_M0/M1/AUX` 用 → **干净** | 无 |
| **PB10 / PB11** | `lora_e22.h` 的 `SYS_LORA_UART = SYS_USART_3`（USART3_TX/RX 就是 PB10/PB11）与 `sys_i2c.h` 的 `SYS_I2C2_SCL`(**PB10**) / `SYS_I2C2_SDA`(**PB11**) 是**同一对脚** | 潜在 |
| **PB3 / PB4 / PB5** | `sys_spi.h` 把 `SYS_SPI1_SCK/MISO/MOSI` 与 `SYS_SPI3_SCK/MISO/MOSI` **都定义在这三个脚上**（SPI1 是重映射、SPI3 是默认映射，物理上确实同脚） | 潜在 |
| **PB15** | `sys_spi.h` 的 `SYS_SPI2_MOSI` 与 `lcd.h` 的 `LCD_BL` 同脚 | 潜在 |

板1 `main.c` 同样只 `Init` 了调试串口 + LoRa 用的 USART3，**没开 I2C2 / SPI1 / SPI3 / SPI2**，所以也不是活冲突。

### 9.3 板2 库内其它重叠（与 LoRa 无关，一并记录）

- `PA2`：`sys_usart.h` 的 `SYS_USART2_TX`（板2 是 Qt 上位机口）与 `sys_eth.h` 的 `SYS_ETH_MDIO` 同脚；`PA1`/`PA7` 也被 `sys_eth.h` 的 `SYS_ETH_REFCLK`/`SYS_ETH_CRSDV` 占用。**`SYS_ETH_ENABLE 0`（默认关）所以不炸** —— 而且板2 原理图上"以太网模块接口(CN4)"那个块画的实际是 NRF24L01 插座（原作者笔误），本板没有 PHY。
- `PG8`：`sys_rs485.h` 的 `SYS_RS485_DE_PIN` 与 NRF24L01 的 IRQ 脚。

### 9.4 结论与建议

**这些重叠全部是"库级潜在冲突"，当前 `main.c` 里一个都没激活。** 但它们说明一件事：**这两个模板库的引脚宏是"每个模块各自声明一个看起来合理的默认值"，没有全局引脚分配表，也没有编译期冲突检查。**

上板联调时如果出现"某个模块单独测正常、一起跑就乱"，第一件事就是回到这一章逐脚核对。三条建议**已于 2026-10-11 全部落地**：

1. 【已处理】 **板2 的 LoRa 三个脚已改成原理图确认空闲的脚（PE5/PE6/PE7）** —— 只改 `lora_e22.h` 3 个宏，`.c` 一行未动。见 §9.1。
2. 【已处理】 **两板 `main.c` 顶部已加"本板引脚占用表"**：逐脚列出占用者（同脚被抢的标 `注意：`），并写明三份权威来源：本表 / `python 本地工具\仓库巡检\pin_audit.py`（静态扫描 `#define X_PORT`+`X_PIN` 配对，结果写 `_pin_audit.txt`）/ 运行期 `GPIO_ClaimDump()`。这段表由 `本地工具\仓库巡检\sync_main.py` 幂等维护，**手改会被下次重跑覆盖**（要改就改脚本里的表再重跑）。
3. 【已处理】 **`gpio_core.c/.h` 已加引脚占用登记**：`uint8_t GPIO_Claim(GPIO_TypeDef *port, uint16_t pin, const char *who)`（返回 0=首次 / 1=同文件重复或端口为 0 / **2=被另一个文件占了** / 3=登记表满，表 96 条）；冲突时**当场打印** `[GPIO_Claim] CONFLICT xN : 文件A:行  vs  文件B:行`，另有 `GPIO_ClaimConflictCount()` / `GPIO_ClaimLost()` / `GPIO_ClaimDump()` 供上板时打一份全表。两板 `main.c` 的自检末尾（`test_mqtt()` 之后、建任务之前，登记已满且仍是单线程）已插一句 `GPIO_ClaimDump();`。
   注意：**关键设计**：`gpio_core.h` 把 `GPIO_Init` / `GPIO_OutInit` / `GPIO_OutInitOD` / `GPIO_InInit` 重定义成转发到带 `who` 形参的 `*Ex` 版，并自动用 `__FILE__ ":" __LINE__` 填 `who`，**全库既有的几百处调用一行都没改，就已经全部登记**（实测所有调用者都 `#include "gpio_core.h"`，覆盖率 100%）。冲突判据是"同一 (端口,位号) 被**两个不同源文件**登记"，**同一文件内重复不算**（单总线器件本来就要反复切方向，例如板1 `sys_dht11.c` 有 `OutInitOD`×1 + `InInit`×3）。
    **为什么不用编译期断言**：试过 `typedef char PIN_ASSERT_x[cond ? -1 : 1]` 这套：板2 的"LoRa 口 ≠ ESP8266 口"（纯整型宏比较）能过，但板1 那条一碰 SPL 的 `GPIOA`（展开成 `((GPIO_TypeDef *)GPIOA_BASE)`）就报 `#183: type of cast must be integral`，换 `#if` 也不行（预处理表达式不许强制转换与指针），实测 5 Error 后撤掉，改为"文档 + 运行期登记"两道防线。这也正好是 `GPIO_Claim` 比编译期断言更强的地方：它管**所有**脚，不只 PA2。

### 9.5 两板 `main.c` 实际是"同一份双板共用源"，各自带着另一半的死代码

这一节不是引脚问题，但同样属于"上板前必须知道"的工程结构事实 —— 它解释了一个看起来很矛盾的现象。

- 实测行数：板1 `S_N_sys\Project_1_检测端\Project\main.c` = **1256 行**；板2 `S_N_sys\Project_2_数据通信端\Project\main.c` = **1265 行**。两者只差 9 行。
- 注意：**2026-10-11 已把板号从文件里挪进工程配置**（原来两板差异的根源，就是各自开头那 4 行的默认值 `1` / `2`）：
  - 板1 `标准模板.uvprojx:337` 的 `<Define>` = `USE_STDPERIPH_DRIVER, STM32F40_41xxx, HSE_VALUE=8000000, SYS_TEST_BOARD=1`；板2 `000标准模板库.uvprojx:337` 同样前三个宏 + `SYS_TEST_BOARD=2`。
  - 两个 `main.c` 顶部改成**兜底**：没定义板号（或定义成 1、2 之外的数）就 `#error "没有定义 SYS_TEST_BOARD（应由 Keil 工程的 C/C++ Define 给出 1 或 2）"`，文件里再也搜不到 `#define SYS_TEST_BOARD` 这个字面量。
  - 以后**改板号改 `.uvprojx`，不要再改 `main.c`**；`.uvprojx:355` 的另一个 `<Define></Define>` 属于汇编器（`<Aads>` 段），不要动。
  - 顺带把 `本地工具\仓库巡检\sync_main.py` 里"把板1 文本里的 `SYS_TEST_BOARD 1` 替换成 `2` 生成板2"那句删了：板2 现在是板1 的**整份副本**再叠两条板2 专属插入（`esp8266.h` / `mqtt.h` 两个头、时间戳读取改 `SysRtc_t`），并带"板2 里不许再出现 `#define SYS_TEST_BOARD`"的护栏。
- 于是满篇的 `#if (SYS_TEST_BOARD == 1)` / `#if (SYS_TEST_BOARD == 2)` 把**另一块板的分支整段编译掉**。板1 那份的 `main.c:86-91`（`#else` 分支：`#include "w25qxx.h"`、`#include "w25qxx_log.h"`、`#include "modbus.h"`、`#define HAS_W25QXX 1`）**永远不参与编译**。
- 注意：**这就解释了那个矛盾**：板1 的 `FWLIB` 里根本没有 `w25qxx.c/.h`、`w25qxx_log.c/.h`（全仓库 `w25qxx*` 只存在于 Project_2），而板1 的 `main.c` 里明明写着 `W25QXX_ReadID()`（`:314`）、`W25QXX_Init(0U)`（`:328`）、`W25QXX_LogInit()`（`:353`）、`W25QXX_LogWrite()`（`:373`、`:923`），还有第 07 项「断网缓存日志（S1/S2 修复验证）」自检：**这些在板1 上全是死代码**：`HAS_W25QXX` 在板1 分支里没被定义，`#if HAS_W25QXX` 展开成 `#if 0`。板1 能 0 Error 编译通过，正是因为它们根本没进编译器。
- 对称地，板2 那份里 `#if (SYS_TEST_BOARD == 1)` 的分支（DHT11 / LoRa / `SYS_MODBUS` / `HAS_DHT11`）同样是死代码。
- **影响与结论**：
  1. **不要试图"两板 `main.c` 逐字节同步"**：它们本来只差 9 行，但也正因为只差 9 行，**改一个就必须同步改另一个**（`FRAME_TOTAL`、`SYS_FRAME_*` 用法、喂狗任务个数这类常量尤其容易漏）。§7.2 的"可整文件同步清单"里**不含** `main.c`，原因就在这里。
  2. **板1 固件实际上没有 Flash 断网缓存功能**（模块都不在）。这与架构设计一致：断网缓存本来就该在**有 4G/MQTT 上行的那一端（板2）**，板1 只负责"采集 → 组帧 → LoRa 发出"。因此 §0 缺口第 3 条那张「11 项自检」对照表里，**第 06 项（Flash 身份）与第 07 项（断网缓存日志）只对板2 有效**。
  3. **风险提示**：哪天有人在板1 工程里把 `<Define>` 的 `SYS_TEST_BOARD` 写成 2（或在两个工程间混用 `main.c`），板1 会立刻因为找不到 `w25qxx.h` 而编译失败 —— 新的 `#error` 兜底让它在**编译期**就吼，不必等人上板时去猜"为什么板1 的第 7 项自检不打印"。
  4. 【已处理】 **原来"更彻底的做法"的后半句已做**：`SYS_TEST_BOARD` 已挪进各工程 `<Define>`，`main.c` 顶部用 `#if (SYS_TEST_BOARD != 1) && (SYS_TEST_BOARD != 2)` → `#error` 兜底。**仍未做的前半句（属结构重构）**：把两板共用部分抽成 `app_common.c/.h`，每块板只留一个薄的 `main.c`。
