# 上板验证步骤（DHT11 最小闭环至全链路）

> 配套程序：`S_N_sys\Project_1_检测端\Project\main.c` 与
> `S_N_sys\Project_2_数据通信端\Project\main.c`
> 这两份 main.c 是自检与最小闭环联调程序，逐条验证审查中已修复的问题。
> 编译结果：板1 `0 Error 0 Warning`、板2 `0 Error 0 Warning`。

---

## 0. 必须上板运行的原因

两块板原来的 `main.c` 是空骨架，链接器把全部驱动当死代码裁掉。
用 `fromelf` 反查 `.axf` 符号表可以证明：修复前后 `Code` 都是 3928 字节，
映像里除 `main` 和 FreeRTOS 之外没有其他符号，
`W25QXX_ReadID`、`MQTT_*`、`SYS_ADC_Read` 都不在映像里。

所以：

| 信号 | 实际情况 |
|------|----------|
| `0 Error / 0 Warning` | 几乎无信息量：编译器没有检查驱动能否运行 |
| `Program Size: Code=3928` 没变化 | 不能说明改动没生效，只能说明驱动没有被引用 |

现在换上这份 main.c，主动调用每个驱动：

| | 修复前 | 现在 |
|---|---|---|
| 板1 Code | 3928 | **26868** |
| 板2 Code | 3928 | **27680** |

驱动已进入映像。但"能编译"不等于"能运行"，下面说明运行方法。

## 1. 硬件准备（接线错误会烧毁模块）

### 1.1 两块板共同操作

1. 连接串口线到 USART1（板载 CH340C），串口助手设为 115200 8N1。
   - 板2 注意：USART1 到 CH340C 之间要插两枚跳线帽
     （`PA9T ↔ URXD`、`PA10R ↔ UTXD`），不插则收不到任何数据。
2. 连接 LoRa 天线后再上电。不接天线发射会烧功放，且不可逆。
3. 接好 LoRa 的 M0/M1，不得悬空。模块内部没有上拉，
   悬空会随机进入配置模式，现象是"AT 有时通有时不通"。

### 1.2 接线表

| | 板1 检测端 | 板2 数据通信端 |
|---|---|---|
| 调试口 | USART1（PA9/PA10，板载 CH340C） | USART1（同上，**需跳线帽**） |
| LoRa 串口 | **USART3**（PB10/PB11，原 ESP8266 座） | **USART6**（PC6/PC7，P1 排针） |
| LoRa M0 / M1 / AUX | PB0 / PB1 / PB2 | PE5 / PE6 / PE7（2026-10-11 由 PA4/PA5/PA6 改来） |
| DHT11 | **PG9**（板载） | 无 |
| W25QXX Flash | 无 | SPI1（与 NRF24L01 共用一组脚，**两者不能同时用**） |

> 换板或换接线只需改各驱动 `.h` 里的宏：LoRa 见 `lora_e22.h` 的
> `SYS_LORA_UART` / `SYS_LORA_M0_*`；DHT11 见 `sys_dht11.h` 的
> `SYS_DHT11_PORT/PIN`。`.c` 不用动。

## 2. 第一步：仅验证板1 的 DHT11（最小闭环）

先只烧录板1，暂不接 LoRa。板上电后串口助手应显示：

```
################################################
#    SPL + FreeRTOS 模板库   上板自检与闭环联调   #
#   板号 : 1 —— 板1 检测端 (Project_1_检测端)
#   编译 : <日期> <时间>
################################################

------------------------------------------------
  01 复位原因
------------------------------------------------
  复位标志 = 0x...
  解码     = ...
  [ OK ] 复位原因可读
...
------------------------------------------------
  08 DHT11 温湿度（D1 修复验证）
------------------------------------------------
  第 1 次: 返回 0  裸字节 3C 00 19 00 55
  温度 = 25.0 ℃   湿度 = 60.0 %RH
  (DHT11 的小数位实际为 0，这是器件特性不是读错)
  [ OK ] DHT11 读成功（位相位已修正）
```

### DHT11 通过判据

裸字节行是判据，字段格式为 `[湿度整数][湿度小数][温度整数][温度小数][校验和]`，
校验和 = 前 4 字节之和（本例 `0x3C+0x00+0x19+0x00 = 0x55`）。

三种失败形态与含义：

| 裸字节 | 含义 | 查什么 |
|---|---|---|
| 全 `FF` | 总线一直高，器件没应答 | PG9 接线、供电、上拉电阻 |
| 全 `00` | 总线一直低，引脚被拉死 | 引脚号是否填错、方向配置 |
| 个别位不同 | 时序被中断打断 | 确认 `SYS_DHT11_LOCK_IRQ = 1` |

> 修复前的现象：`sys_dht11.c` 的应答段少一次等待，位相位错一位，
> 校验和不成立，`SYS_DHT11_Read()` 返回 `-2`。
> 修复后应稳定返回 `0`。

### 其他检查项

- 03 毫秒时基：`SYS_TICK_GetTick()` 必须增长，间隔 40~60ms。
  修复前它恒为 `0`，且 `SYS_TICK_Delay_ms()` 会永久死等。
- 05 看门狗：`HeartbeatPoll()` 在库默认配置（`SYS_WDG_HEARTBEAT_COUNT = 0`）
  下必须返回非 0。修复前它是 no-op。按 `sys_wdg.h` 注释写
  （"主循环只留一句 HeartbeatPoll()"）会进入上电复位循环。
- 04 微秒延时：`SystemCoreClock` 应为 `168000000`。

## 3. 第二步：LoRa 两点对通

### 3.1 两个模块配对

两端的网络 ID、信道、地址三项必须完全相同，否则收不到数据。
用板1 的 `LORA_E22_ReadConfig()` 输出确认，自检 09 会打印：

```
  模块配置 = AT+VER=... AT+ADDR=1234 AT+NETID=18 AT+REG0=...
  两端要互通，网络ID / 信道 / 地址 三项必须完全相同。
```

需要修改时，把下面这句放进 `main()` 执行一次，然后断电重启：

```c
(void)LORA_E22_SendAT("AT+NETID=18");
(void)LORA_E22_SendAT("AT+ADDR=1234");
/* 一般只改 NETID 和信道，其余保持出厂 */
```

### 3.2 两块板同时上电

- 查看板1 输出：每 2 秒打印一次 `[处理] 组帧 20B: AA 55 01 0C ...`，随后打印 `[发送] 已发出第 N 帧`
- 查看板2 输出：每收到一帧打印 `[接收] 第 N 帧合法: T=25.00℃ H=60.00%RH`

板2 的完整输出分三段：

```
[任务] LoraRxTask 启动
[任务] ForwardTask 启动
[接收] 第 1 帧合法: T=25.00℃ H=60.00%RH
[处理] 已缓存 1 条 / 失败 0 条，Flash 里共 1 条待补传
[监控] tick=12000  LoRa: 收到 1 帧 / 坏帧 0 个 | Flash: 缓存 1 条 / 失败 0 条
```

### 3.3 故障排查

| 现象 | 最可能的原因 |
|---|---|
| `LORA_E22_Init()` 返回 1 | AUX 一直忙：模块没上电 / M0M1 接错 / 电源去耦不够 |
| `LORA_E22_SendAT("AT")` 返回 2 | 没接 M0M1；本端波特率不是 9600；TXD/RXD 接反 |
| 返回 3 | 指令拼错（注意逗号、结尾必须 `\r\n`） |
| 板1 在发、板2 收不到 | 两端 NETID / 信道 / 地址不一致（最常见） |
| `[接收] 坏帧` 一直涨 | 距离太近没接天线导致丢包 / 电源去耦不够 |
| 能发不能收 | TXD/RXD 接反（模块 TXD 要接 MCU RX） |

### 3.4 帧格式（对照 `[处理]`/`[接收]` 打印自查）

20 字节整帧，CRC16-MODBUS 范围是 `[2..15]` 共 14 字节，低字节在前：

```
[0][1]   0xAA 0x55            帧头
[2]      0x01                 命令：环境数据上报
[3]      0x0C                 数据段长度 12
[4..15]  数据段（大端）        温度×100 / 湿度×100 / 气压×10 / 光照 / TVOC / MQ135
[16][17] CRC16（低字节在前）    范围 [2..15]
[18][19] 0x55 0xAA            帧尾
```

板2 的解析做三重确认：帧头 + 长度字段 + 对整帧再算一遍 CRC 必须为 0。
这一条同时排除了帧尾 `0x55AA` 与下一帧帧头 `0xAA55` 粘连导致的错位。

> 注意：气压字段是 ×10，不是 ×100。`1013.25 × 100 = 101325` 超出 `uint16` 上限。

## 4. 第三步：Flash 断网缓存（板2 关键项）

这一步验证断网缓存功能能否成立。

### 4.1 首次烧录后的输出

```
------------------------------------------------
  06 Flash 身份（S4 修复验证）
------------------------------------------------
  JEDEC ID = 0xC84018
  厂商     = 0xC8  (GigaDevice 兆易创新)
  容量字节 = 0x18  (0x18 = 128Mbit = 16MB，即 GD25Q128)
  W25QXX_Init() = 0  (0=成功 1=没器件 2=容量不符)
  [ OK ] W25QXX_Init 接受非 Winbond 的 128Mbit 器件
```

`JEDEC ID` 应为 `0xC84018`（GigaDevice GD25Q128）。
修复前 `W25QXX_Init` 只识别 Winbond 的 `0xEF4018`，而本板不是 Winbond，
因此 `Init` 返回 1，调用方按 `w25qxx.h` 的示例
`if (W25QXX_Init(0) != 0) return;` 会直接跳过整个缓存模块。

### 4.2 查看日志段

```
------------------------------------------------
  07 断网缓存日志（S1/S2 修复验证）
------------------------------------------------
  W25QXX_LogInit() = 0
  上电时已有 0 条 / 容量 1024 条 / 写指针 0 / 已丢 0 条
  写入后 W25QXX_LogCount() = 3
  读回 index=2 ts=1002 len=9 text="TEST-REC-2"
  [ OK ] 写入的记录能被数出来（状态字写成 VALID 了）
  [ OK ] 读回内容与写入一致

  断电再上电后重看这一段：
    若上电时打印的 count ≥ 3 且能读出 TEST-REC-2，则 S1/S2 通过。
```

### 4.3 断电重启

把板2 断电，等 2 秒，再上电。重看"上电时已有 N 条"这一行：

| 结果 | 结论 |
|---|---|
| `已有 3 条`，且能读出 `TEST-REC-2` | S1（状态字）+ S2（扇区擦除）通过，断网缓存成立 |
| 又变回 `0 条` | 状态字没真正落盘，回到 S1 查 |
| `已丢 N 条` > 0 | 缓存绕圈覆盖过（断网太久或补传太慢），应报警或加大分区 |

> 修复前的现象：`w25qxx_log.c:222` 把状态字写成 `W25QXX_LOG_EMPTY`
> 而不是 `VALID`，因此每条记录都被判成空槽，`LogCount()` 恒为 0、
> `LogInit` 扫描出 0 条。现象是写入不报错、补传永远 0 条，
> 即断网缓存功能不成立，且不报任何错误。

### 4.4 补传通路（08b 项）

07 项之后紧接打印 08b。这一段会真跑一轮补传：写 5 条合成环境帧 → 触发补传 →
逐条以 `0x15` 历史帧上报 → 收尾清空缓存。标号带 `b` 是因为串口上 DHT11 已占 `08`。

```
  写入 5 条合成环境帧，时间戳 101010 ~ 101014
  写入完成：W25QXX_LogCount() = 8，补传在调度器启动后由补传任务执行
  ...
[自检 08b] 触发补传：共 8 条，每 50 ms 一条
[补传] 1/8 ts=1000 帧前 4 字节 = AA 55 01 0C
...
[补传] 本轮发完：已发出 8 条，跳过 0 条，补传期间丢弃新帧 0 条（不补发）
[补传] 开始清空 Flash 缓存（挂起调度器约 0.5~1s，期间不切任务）
[补传] 清空结束：返回 0（0=OK），剩余 0 条，累计丢 0 条
[自检 08b] 补传条数 8 条 / 跳过 0 条 / 补传期间丢弃 0 条，清空后 W25QXX_LogCount() = 0，W25QXX_LogLost() = 0
  [ OK ] 补传条数不少于写入条数
  [ OK ] 补传收尾后缓存已清空
[自检 08b] 完成，补传状态回到空闲（与 0x16 停止命令同一条路径）
```

条数是 8 而不是 5：07 项先写了 3 条，补传从缓存头部开始，所以一轮扫的是 8 条。

判据：

| 结果 | 结论 |
|---|---|
| 两行 `[ OK ]` 都在 | 补传通路成立：能读回缓存、能按 `0x15` 上报、收尾能清空 |
| `缓存里有 N 条记录，不全是自检写进去的：本项跳过` | 缓存里有真实断网数据，本项主动跳过（一轮补传会整片擦掉）。先发 `0x13` 清一次缓存或让缓存排空，再复位 |
| `等 8000ms 仍未收尾` | 补传任务卡住，查 `W25QXX_LogRead` 返回值与 SPI1 占用 |
| `跳过 N 条` 不为 0 | 缓存里有空洞或坏记录（扇区擦除留下的），属正常容错，但应记录 |

> 补传只由上位机 `0x16` 或本项触发，不会自动开始。板2 侧不记"已补传位置"，
> 掉电重启后从头补传，去重由上位机按"原始时间戳 + 20 字节原帧"完成。

上位机侧配合验证：点"补传历史数据"按钮 → 板2 回 `0x96`，界面显示已补传/剩余条数；
CSV 里这些行的"数据来源"列应为"补传"，时间戳是记录里的原始时间戳，不是到达时刻。

## 5. 第四步：全链路跑通后的监控数字

板2 的监控行每秒输出一次，联调稳定后应为：

```
[监控] tick=30000  LoRa: 收到 15 帧 / 坏帧 0 个 | Flash: 缓存 15 条 / 失败 0 条
```

- 核对收到帧数 ≈ 运行秒数 ÷ 2（板1 每 2 秒一帧）
- 核对坏帧 0：有坏帧说明空口丢包或两端参数有细微不一致
- 核对失败 0：Flash 落盘失败说明 SPI1 有问题（注意不要与 NRF24L01 争用总线）
- 核对 Flash 缓存条数：离线期间持续增长属正常，联机后由上位机点"补传历史数据"
  触发补传（`0x16`），补传完成会清空缓存，条数回 0；补传期间新到的帧只计数不补发
  （串口打印"补传期间丢弃新帧 N 条"）

## 7. 修改 main.c 的注意事项

1. 确认文件为 GBK 编码。AC5 实测要求：同一份内容存成 UTF-8 会报
   30 个 `#8: missing closing quote` / `#870-D: invalid multibyte character
   sequence`，存成 GBK 则 `0 Error`。改完确认编码未被编辑器改回 UTF-8。
2. 避免在字符串中写"中文后紧接引号"。GBK 下某些汉字的第二字节会吃掉
   紧跟的 `"`，同样报 `missing closing quote`。处理方法：中文后留一个
   空格，或使用「」，或改用全角标点。
3. 两份 main.c 由脚本同步：`本地工具\仓库巡检\sync_main.py`（幂等，可重复运行）
   负责 ① 板1 的 RTC 声明块包壳 ② 板1 的组帧段包壳 ③ 由板1 生成板2 并
   改为 `SYS_TEST_BOARD = 2` + 补板2 的 `SysRtc_t` 时间戳写法。
   修改板1 的 main.c 后运行一次该脚本，两板才不会各改一半。
4. 注意两板 `sys_rtc` API 不同（历史遗留）：板1 是 `SYS_RTC_GetDate()` +
   `SYS_RTC_GetTime(h,m,s)`；板2 是单个 `SysRtc_t` 结构体。
   `main.c` 里用 `#if (SYS_TEST_BOARD == 1)` 抹平。
5. 看门狗必须在启动调度器之前 `Init`。前面 DHT11/LoRa 自检需十几秒，
   提前开狗会在自检途中把板子复位，表现为"程序跑不起来"。
6. 自检阶段不要用 `delay_ms()`，统一用 `delay_ms_dwt()`。
   `delay.c` 的 `delay_ms()` 是未标定忙等，且 RTOS 下语义不明确。

## 8. 下一步

上板跑通后，剩余工作如下（按《代码审查报告.md》的顺序）：

1. 处理 §3 的约 40 条待办，最优先是 `mqtt.c:490-500` 的心跳判活。
   现在只发 `PINGREQ` 不检查 `PINGRESP`，半开 TCP 下 `s_connected` 恒为 1，
   而它是"断网后转 W25Q 缓存"的触发判据，判据不可靠会导致数据静默丢失。
2. 补驱动缺口：板1 缺气压（BMP280）/ 光照（BH1750）/ 空气质量（CCS811）。
   I2C 器件都走 SHT30 那一套 `SYS_I2C_WriteReg16/ReadReg16`（16 位命令）。
3. 统一协议：`sys_frame` 现在仍是单字节 `0xAA`/`0x55` + 异或校验，
   与本项目定稿的双字节 `0xAA55`/`0x55AA` + CRC16-MODBUS 20 字节帧不一致，
   属改造而非配置（F1/F2 已修好并发与越界，改造时不用再动那两块）。
