# 嵌入式工具箱规划

本文件是 `本地工具/工具箱/` 的规划存档。来源是一份问卷。
问卷结论、工具取舍、实现形态与排期都记在这里，供后续对照与打勾。

说明：工具箱内是本次开发新建的工具；`本地工具/` 下的其他目录（一键上传、仓库巡检、
标准库速查、标准库速查手机版、面试刷题）为原有工具，不在本规划内，保持原位。

## 1. 使用者现状（问卷结论）

| 维度 | 现状 |
|---|---|
| 阶段 | 转行初期，嵌入式经验不足 1 年，待业，独自开发 |
| 语言 | C / C++ / Qt 中等；Python、JS 只会看；PowerShell 略懂 |
| 硬件 | 焊接与逻辑分析仪可用；画板不熟 |
| RTOS | FreeRTOS 初学；中断优先级约束不清楚 |
| 最耗时 | 项目起头时的思路构建、模块之间的协调与联动 |
| 已点名的风险 | 协议一致性、引脚冲突、编码乱码、RTOS 优先级与栈溢出 |
| 目标权重 | 能力提升(1) > 方法论沉淀(2) > 加速项目(4) = 面试作品(4) |
| 工具角色 | 要检查拦截、要教方法并留出动手空间；不接受全自动代做 |
| 投入与环境 | 每天 2 小时以上；Python、Qt、git、Node 齐全；无分发限制；要求双击即用 |

结论：缺的不是"代写代码的工具"，而是资深工程师的起手套路与随时可用的反馈回路。
工具按检查员加教练的定位设计。

## 2. 设计原则

1. 高频日常优先。现有工具好用但低频，除"标准库速查"外平时不常开。新工具要能每天用到，或嵌入现有流程。
2. 先解决当前项目，同时沉淀方法论。工具输出尽量对齐本仓库已有的文档写法（如 `设计思路报告.md`）。
3. 形态服从可维护性。主力用 Qt C++ 桌面应用（使用者最能读懂维护，环境已有，可打包双击运行）；辅助用 Python 脚本加 bat（只运行不改内部）。
4. 少铺开。手机端与 VS Code 插件暂缓，避免做成"要维护却不擅长"的负担。
