## 阶段8：一按复位就卡在 boot…（插着 J-Link 必现）



现象:程序烧好后按复位键,串口只打印一行 `[board1] boot...` 就再也不动了,LED 也不按 0.2 秒流水走,看起来像固件死在启动流程里。但是一接上 J-Link 读一次内存,程序又自己跑起来了,而且每次复位都复现。



排除:

1. 先怀疑固件卡在 LoRa 初始化(`main.c` 里 `E22 init=%u` 的打印在函数调用之后,卡在里面就只剩 boot 那一行),但接上调试器后能一路跑到 RUN,不像。

2. 读 `RCC_CSR`(0x40023874) = 0x00000002,只有 LSION 位,**没有任何复位标志**,说明不是看门狗复位、不是欠压复位,更不是复位循环。

3. 间隔 3 秒读三次 `xTickCount`(0x200000C0):53853 → 56855 → 59856,每 3 秒 +3000,说明调度器一直在正常跑。

4. 读 `s_state`(0x20000090)=1(RUN)、`s_fault_done`(0x2000009C)=0、`s_tx_ok`(0x20000008)=30、`s_dropCnt`(0x20000000)=0,全部正常。



原因:J-Link 连着的时候,调试器通过 SWD 把内核按在 halt 状态(DHCSR 的 C_HALT),内核停在原地不执行,直到调试器发 Go。所以现象是“打印完 boot 就不动”,看起来和真死机一模一样。用 J-Link 命令行发一条 `g`,tick 立刻开始涨,实锤是被 halt 住的,不是固件 bug。



解决:把 J-Link 的 USB 线从电脑上拔掉,再按复位,板子正常启动并持续运行。以后调试完要么点 Go 释放,要么直接拔线再测。



怎么快速区分“真死机”和“被调试器按住”:

- 读 `RCC_CSR`:有 IWDGRSTF/PORRSTF 等标志 = 真在复位;全 0 = 不是复位问题

- 隔 3 秒读两次 `xTickCount`:不涨 = 内核没跑;发 `g` 后涨 = 被 halt

- 串口停在固定某一行 = 执行到那儿之后停住,再配合上面两条判断

# 阶段9：联调当天遇到的一批问题（2026-10-23）

## 问题1：插上 OLED 后，板1 卡在 `[board1] boot...`，指示灯全灭
- **现象**：串口只打一行 boot 就停，四个灯不亮，按复位无效
- **排除**：拔掉 OLED 立刻全链路正常（E22 init=0 → HCLK → 4 路传感器全读到）
- **原因**：OLED 和 5 个传感器共用一颗 AMS1117-3.3，插上后 3.3V 被拉跌，MCU 掉电/挂死
- **解决**：暂时不接 OLED；新底板给模块独立 LDO + 每座 0.1µF 去耦

## 问题2：板1 串口一个字节都收不到，但 J-Link 看程序在正常跑
- **排除**：USART1 寄存器全对 —— `BRR=0x02D9`(115200)、`CR1=0x200C`(UE/TE/RE)、`SR=0x00C0`(TXE/TC 无错)、`PA9` 空闲高、`DR=0`（一个字节都没进来）
- **原因**：USB 扩展坞单口**过流保护**。LoRa 发射瞬间 120mA 把 CH340 一起拉掉线（COM7 → COM9 跳变）
- **解决**：换一个 USB 口；长期用 DC 5V/2A 给板子单独供电

## 问题3：SHT30 读数据 `rc=-4`（数据段 NACK），但地址能扫到 0x44
- **现象**：`init=0` 成功、扫描有 0x44，一读数据就 NACK，100% 复现
- **排除**：驱动里做 4 种协议候选（SHT3x 拉伸/不拉伸、SHT4x 高/中精度）能命中，说明芯片和驱动都没问题
- **原因**：4 个 I2C 模块每个自带 4.7k 上拉，**并联后只有 1.18k**，灌电流 2.8mA；再叠加面包板 + 杜邦线的接触电阻和寄生电容，从机拉不到 VOL(0.4V)
- **解决**：I2C 从 100kHz 降到 **50kHz**；新底板上拉电阻默认不焊

## 问题4：I2C 总线跑一阵就"死"，软件复位无效，只有断电才好
- **机制**：I2C 是开漏结构，SDA 控制权会临时交给从机；从机停在"输出 0"就不释放总线，主机做什么都没用
- **为什么超时救不回**：超时只能让**主机**放弃，从机根本不听 STOP
- **为什么 9 个 SCL 脉冲也没用**：它只能救"从机在等时钟"，救不了"从机内部死机 / 掉电复位"
- **解决**：断电；代码里加"连续 3 轮全失败 → 重初始化 I2C + 解除所有器件隔离"，再加单器件离线隔离（连续 8 次失败跳过，每 30 轮重探）

## 问题5：采样周期设定 2 秒，实测 4 帧/秒
- **原因**：`vTaskDelayUntil` 在任务被拖慢之后会一直"追赶"，不再真正等待
- **解决**：改绝对节拍 —— 记 `t0` 算 `used`，再 `vTaskDelay(period - used)`

## 问题6：按复位键没用，一插调试器就"卡在 boot"
- **原因**：J-Link/Keil 通过 SWD 把内核按在 halt（DHCSR 的 C_HALT），不是固件 bug
- **解决**：Commander 脚本末尾发 `g`；Keil 勾 **Reset and Run**；或断电重上电
- **判别**：读 `RCC_CSR` 无复位标志 + 隔 3 秒读两次 `xTickCount` 不涨 = 被 halt 住

## 问题7：板2 屏幕全黑，读 ID 得 `0x00032404`（应为 0x009481xx）
- **原因**：`lora_e22.h` 把 LoRa 的 AUX 配到 **PE7**（输入上拉），而 PE7 是 LCD 的 **FSMC_D4** 数据线 → 数据被抢，命令/数据错位
- **解决**：注释掉 `SYS_LORA_AUX_PORT/PIN`（AUX 本来就悬空）
- **教训**：上电时打印 GPIO 冲突提示；多外设共用引脚一定要有集中分配表

## 问题8：板2 红绿两灯 200ms 同步快闪
- **原因**：`vTaskNet` 里 ESP8266 初始化是一问一答阻塞（`delay_ms` 是 DWT 忙等，不让出 CPU），而 `vTaskMonitor` 优先级最低，2 秒内抢不到 CPU → 心跳超时 → **误判 FAULT**
- **解决**：加 `SYS_IND_Busy(1/0)`，联网期间屏蔽心跳超时判断

## 问题9：板2 `bad` 一直涨、队列 8 条塞满
- **原因**：`vTaskNet` 断网分支 `continue` 直接跳过 `xQueueReceive`，**队列永不消费**，8 条塞满后每帧都算 bad
- **解决**：删掉 `continue` 让数据通路优先；重连加指数退避（4/8/16/32 秒）

## 问题10：板2 缓存显示 2005/2048 快满
- **原因**：日志分区只给 16 个扇区 = 64KB = 2048 条，而 W25Q128 有 **16MB**，只用了 0.4%
- **解决**：扩到 255 扇区 ≈ 1MB ≈ **32640 条**（约 18 小时离线），FONT 分区往后挪到 `0x100000`

## 问题11：板2 屏不刷新，但串口 `rx` 一直在涨
- **原因**：`vTaskUi` 用 `xQueuePeek` 取队列头，而 `vTaskNet` 早把帧取走去写 Flash → 大部分时间 peek 不到
- **解决**：收到帧时另存一份 `s_ui_env` 快照 + `s_ui_dirty` 标志，UI 直接读快照，不再碰队列

## 问题12：Qt 一打开串口，板2 立刻白屏
- **原因**：CH340 的 `DTR#`/`RTS#` 经两颗 S8550(2TY) 接 **BOOT0 / RESET**，这是自动下载电路；`QSerialPort` 打开端口时默认把 DTR/RTS 置为有效 → RESET 被拉低 → MCU 一直复位 → LCD 收不到初始化命令
- **解决**：`open()` 成功后立刻 `setDataTerminalReady(false)` + `setRequestToSend(false)`

## 问题13：Qt 界面卡顿
- **原因**：50ms 定时器里每张卡都调 `setStyleSheet` + `setToolTip`，约 480 次/秒；`setStyleSheet` 会重新解析样式表并 polish 整棵子树
- **解决**：加缓存（`QHash` 记录上次的样式/提示，值没变直接 return）

## 问题14：ESP8266 四个波特率全无应答
- **排查**：把 PB10/PB11 短接做环路测试，串口打出 `[NET] 环路回读 原始回复: AT` → **证明 MCU 侧收发完全正常**
- **结论**：问题在模块侧（供电 / CH_PD 没拉高 / 接线）
- **教训**：先用环路把"MCU 侧"和"模块侧"切开，再去查模块

# 排查提问清单（今天总结的通用套路）

> 写下"遇到这个现象，先问自己哪三个问题、量哪两个数"，下次就不用从头猜。

## 一、总原则

1. **先切分，再深挖**：把系统劈成两半，用一次实验判断问题在哪半边，不要一上来就读代码。
2. **一次只改一个变量**：同时改两处，出结果也说不清是谁的功劳。
3. **要能"看见"**：任何判断都要有一个可读的数字（计数器 / 寄存器 / 电压），不能靠"感觉"。
4. **先怀疑物理层**：面包板、杜邦线、供电，比代码容易出问题得多。

## 二、按现象查

### 现象：程序像卡死 / 灯不亮 / 只在第一行停住

| 引脚真的在发吗？ | 读 `USART1->SR` 与 `GPIOA IDR` | `SR=0x00C0` 且 PA9=1 = MCU 侧没问题，断点在线或 CH340 |

## 问题15：板2 屏幕有程序却"没反应"，按复位键也不管用

- **现象**：串口 `rx` 在涨、`bad=0`、帧内容解码出来 25.95℃/63.87% 完全正确，但屏幕一直停在启动菜单
- **排除**：用串口把收到的 20 字节帧逐字节解码，数据是新的 → 链路和解析都没问题，只是"没画到屏上"
- **原因**：之前几次调试时，Qt 的 DTR/RTS 和 ST-Link 都把 **MCU 复位**过，但 **LCD 面板一直有电、从没掉电**。ILI9481 内部还停在上一条命令的状态，MCU 重新上电后发的初始化序列它当成乱码，于是面板和 MCU"各说各话"
- **解决**：**拔掉板2 电源停 5 秒再插上**（不是按复位键），让面板也重新上电 —— 屏幕立刻正常显示
- **教训**：
  - **"MCU 复位" ≠ "整机上电"**。带独立控制器的外设（LCD、WiFi 模块、传感器的内部状态机）都只认自己的上电复位
  - 排查"数据到了但显示不对"时，先分清是**数据问题**还是**显示问题**：解码一帧原始字节就能一刀切开

## 问题16：告警阈值不能照抄国标，要先量本地基线

- **现象**：气压上限设 1020 hPa，但设备装在重庆，读数一直是 978~985 hPa —— **这条告警永远不会触发**
- **原因**：气压随海拔下降，`P = 1013 × (1 - 2.25577e-5 × h)^5.25588`。重庆主城海拔约 250 m → 当地常年约 983 hPa
- **同理湿度**：重庆秋冬多雾，常年 70~85%，用通用的 80% 上限会**天天误报**
- **解决**：先查本地气候与海拔，再定量程：
  | 参数 | 原值 | 改为 | 理由 |
  |---|---|---|---|
  | 温度上限/下限 | 30 / 5 ℃ | **28 / 12 ℃** | 10 月重庆日均 18~19℃，夜间最低 14~16℃ |
  | 湿度上限/下限 | 80 / 20 % | **88 / 35 %** | 当地常年 70~85%，80% 会常态化误报 |
  | 气压上限/下限 | 1020 / 无 | **995 / 970 hPa** | 当地基线 ≈983 |
  | 光照上限/下限 | 800 / 无 | **2000 / 20 lx** | 室内桌面 100~500 lx |
  | TVOC 上限 | 1000 ppb | 1000 ppb | CCS811 未老化，暂放宽 |
- **顺带加的**：回差（温度 1℃、湿度 5%、气压 1hPa、光照 5lx），避免在临界点反复跳变；低压与低光照新开了 `AL2_PRESS`/`AL2_LIGHT` 两位，UI 上低于下限显示蓝色
- **教训**：**阈值属于"部署参数"，不是"程序常数"**。换个城市、换个季节就该改。面试时这是很实的加分点：说明你知道"标定"这件事

## 问题17：Boot 的"救援态"其实救不了人（变砖风险）

- **现象**：App 区跑飞、下载区又没有待安装固件时，串口只打一行
  `rescue mode: send firmware from PC via the serial link. heartbeat ...` 然后一直打点，PC 发什么都不理。
- **定位**：`boot_uart.c` 初始化只写了 `USART_CR1_UE | USART_CR1_TE`，**PA10 根本没配成复用功能**，
  注释还明确写着"只发，不需要 RXNE 中断"。翻遍 Boot 工程，**没有任何一个接收函数**。
  也就是说那句"send firmware via the serial link"是句空话 —— 喊了救命，但没有耳朵。
- **影响**：这块板子一旦 App 区没有可跑镜像，除了 SWD/J-Link 就再也救不回来。
  "变砖"不是夸张，是字面意思。
- **修法**：
  1. `boot_uart.c` 补 PA10 → AF7、上拉，`CR1` 加 `USART_CR1_RE`，新增 `Boot_UartGetc(spin)` / `Boot_UartFlush()`；
  2. 新增 `boot_rescue.c`（约 260 行）：`S` 写头（擦下载区）/ `D` 按绝对偏移写包 + CRC16 / `E` 整片复验；
  3. `boot_main.c` 把心跳死循环换成 `Boot_RescueLoop()`，写完**回到原来那条唯一的安装路径**
     （不在救援代码里复制第二套搬移逻辑，少一份会走样的实现）；
  4. PC 侧配 `EnvMonitor/项目工具/OTA救援/OTA救援烧写.py`。
- **教训**：**"有一条恢复路径"要能端到端跑通才算存在**。只打印一句话、只开发送不开接收，
  在文档里却写着"支持串口救援"，比没有更危险 —— 出事时你以为有后路。

## 问题18：装进去一个"CRC 对但跑不起来"的固件，就再也回不去了

- **现象**：`OtaImage_AppValid()` 只检查三件事 —— 栈顶落在 RAM、复位向量落在 App 区、Thumb 位为 1。
  这三件都满足的垃圾镜像会被**每次上电都跳过去**，直接挂在 HardFault 里。
- **为什么 CRC 校验挡不住**：CRC 保证"字节没传错"，不保证"这个程序在这块板子上能跑完初始化"。
  初始化一半挂死、外设时序不对、栈溢出 —— 字节都是对的。
- **修法（2026-10-24 已实现）**：Sector 5（`0x08020000`，128KB，目前空闲）做**启动事件日志**：
  Boot 每次想跳 App 前追加"尝试"标记；App 稳定运行后追加"确认"标记；
  Boot 上电扫日志，发现"自上次确认以来尝试 ≥3 次仍未确认" → 不再跳 App，进救援态。
  App 侧在跑满 10 秒后才写"确认"（只确认"初始化完成"挡不住"进主循环才崩"）。
  实现见 `OTA/OTA1/ota/ota_bootstate.c`，Boot 与 App 共编同一份。
- **教训**：**校验和"可运行"是两件事**。固件升级的完整性靠 CRC，可用性靠"启动成功确认 + 回退"。

## 问题19：重接线后四个传感器一个都扫不到——不要先怀疑 I2C 频率

**现象（2026-10-26）**
把线全部重接后，板1 串口开机打印：

```
[I2C] before: IDR=0x3F9B (PB8=1 PB9=1)     ← 总线空闲高，上拉正常
I2C1 scan: 3 dev
  addr=0x1A   ← 板上固有
  addr=0x50   ← 板上固有（EEPROM）
  addr=0x68   ← 板上固有（RTC）
SHT30 init=2        (NO_DEVICE)
BMP280 ID=0xFFFFFFFD  (-3 = ADDR NACK)
BH1750 init Fail
CCS811 init=2
```

**错误的第一反应**：是不是 I2C 频率太低（50kHz）？
**排除**：50kHz 是规范内速率（标准模式 100k、低速模式 10k 都合法），只会让一次读从 0.2ms 变 1ms，**不可能导致"扫不到器件"**。扫描靠的是地址应答，和速率无关。

**真正的判断依据**
- `PB8=1 PB9=1` → 总线和上拉是好的，MCU 侧没问题
- 扫到的 `0x1A/0x50/0x68` 是**板子上本来就有的器件**，不是外接传感器
- 四个目标地址 `0x23/0x44/0x5A/0x76` **一个都没出现** → 传感器根本没接到总线上

**排查顺序（按命中率）**
1. **量传感器 VCC 对 GND 是否为 3.3V** —— 最常见是没供电
2. 面包板电源轨中间是否断开（万用表量两端通断）
3. 是否插到了面包板凹槽另一侧（左右两半不通）
4. SCL/SDA 整体对调（四个同时不通，通常不是单个接反）

**解决**：查到是接线问题，重接后一切正常。
**复验数据**：帧 `AA 55 01 0C 09 E7 1E 05 26 97 00 3A ...` = 25.35℃ / 76.85% / 987.9hPa / 58lx，`SHT30_FAIL=0`。

**教训**
> **"扫不到器件"永远是物理层问题，"读失败"才可能是速率/时序问题。**
> 先看扫描结果里有没有目标地址，再看数据读写的返回值。

## 问题20：板2 频繁"白屏重启"——两个真因

**现象**
打开 Qt 上位机（或串口助手）连上 COM10，板2 屏幕变白、程序重启。

**原因一：DTR/RTS 一键下载电路（命中率最高）**

板2 的 CH340C 把 `DTR#`、`RTS#` 经两颗 **2TY（S8550 PNP）三极管**接到 MCU 的 **RESET** 和 **BOOT0**，这是标准的 STM32 一键下载电路（NodeMCU 同款）。

副作用：**任何程序打开串口时把 DTR/RTS 拉低，就会把 MCU 按在复位状态** → LCD 收不到初始化命令 → 背光亮、屏幕全白。

**验证方法**：关掉所有串口程序，板子恢复正常 → 就是它。

**解决**：
- Qt：连接前 `setDataTerminalReady(false)` + `setRequestToSend(false)`（已改）
- 串口助手：设置里取消勾选 DTR / RTS

**原因二：供电跌落（ESP 连网时触发）**

板2 峰值电流约 **750mA**：ESP8266 发射 300~400 + LCD 背光 130 + LoRa 120 + MCU 70。
USB 扩展坞单口通常只有 500mA → ESP 一尝试连 WiFi，3.3V 塌陷 → 触发 BOR 欠压复位 → 重启 → 再连 → 再塌，形成循环。

**解决**：板2 用 **DC 5V/2A 独立供电**，USB 只做串口。

**如何区分两种原因**

| 现象 | 原因 |
|---|---|
| 一开串口就白屏，关掉就好 | DTR/RTS |
| 一尝试连 WiFi 就重启 | 供电跌落 |
| 每次烧写完必白屏 | ST-Link 烧完内核停在 halt |
| 无规律随机重启 | 供电 |

**硬件根治（画底板时顺手做）**
- LCD 的 RESET 脚接到 MCU 的复位脚（或独立 RC 复位），MCU 复位时 LCD 跟着复位
- 电源加 1000µF 大电容 + TVS，吸收 ESP 的电流尖峰

## 问题21："云端没数据"其实是三层故障叠在一起

**现象**：屏幕没数据、云端没数据、Qt 没数据，看起来像"整个系统坏了"。

**拆开看是三件事**：

```
云端没数据
  ├─ 第一层：板1 传感器全没扫到（接线问题）
  │    表现：帧 payload 全 0，I2C1 scan 只有 3 个板上固有地址
  ├─ 第二层：板2 net=0（ESP 掉线 / 手机热点关了）
  │    表现：rx 在涨、cache 在涨，但 pub=0
  └─ 第三层（假象）：以为 I2C 频率太低
       实际：50kHz 完全正常，与故障无关
```

**逐层验证的方法（顺序不能反）**

| 层 | 看什么 | 正常值 |
|---|---|---|
| 1 采集 | 板1 帧里 T/H/P/L 是否非 0 | 25.35℃ / 76.85% / 987.9 / 58 |
| 2 空口 | 板2 `rx` 是否每 2 秒 +1 | 持续增长 |
| 3 落盘 | 板2 `cache` 是否增长（离线时） | 增长 |
| 4 上云 | 板2 `net=1` 且 `pub` 与 `rx` 同步涨 | net=1、pub=rx |

**最终复验（打通时的数据）**
```
[MON] rx=20 bad=0 pub=20 fail=0 cfail=0 cache=1028/32640 lost=0 net=1
```

**教训**
> 一条链路越长，越要把"没数据"拆成环节逐个验。
> **从源头往末端查**：先确认采集，再看传输，再看接收，最后看云。
> 反过来（从云端往下追）会被中间的假象带偏。
