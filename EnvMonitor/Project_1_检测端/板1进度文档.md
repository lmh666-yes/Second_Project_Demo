### 阶段 4｜传感器采集：把 6 路数据读准

**这一阶段要交什么**：把 6 路环境量读上来：先扫 I2C 认器件，再逐个打通 BMP280 / BH1750 / CCS811 / DHT11 / MQ-135 / 光敏，并且做到“读不到就不填数”。

| 里程碑（每个动作） | 验收判据（怎么算过） | 完成 |
|---|---|---|
| 先用 I2C 扫描把器件认出来 | 串口打印出器件地址列表。看到 0x76 / 0x23 / 0x5A 三条即三颗外接器件都在线；某个地址缺席，就对号查那颗器件的接线与 ADDR 脚。 | ☐ |
| BMP280：气压 + 温度，先读 ID 再读值 | 串口打印 T 与 P：室温下 T 与 DHT11 差 1℃ 以内；P 在 1000 hPa 上下（海拔每升高 100m 降约 12 hPa）。正常模式（0x4F）下芯片连续转换，Read 只等状态位后取最新值；强制模式（0x4D）下 Read 每次都会先触发再等 15 ms，拿到的同样是当次新值——「读到上次结果」只在绕过驱动、自己直接读 0xF7 时才可能出现。 | ☐ |
| BH1750：光照 lux = raw/1.2，过饱和要认出来 | 手机手电筒照上去：raw 变大、lux 跟着变大；遮住器件 lux 掉到个位数或 0。若 raw 打到 0xFFFF（过饱和），用一张纸挡一层光，值应立刻回落——说明饱和判定生效，而不是器件坏了（读原始值时饱和不会以返回码 3 出现，那个码只有 ReadLux 会给）。 | ☐ |
| CCS811：eCO2/TVOC 要等 DRDY，建议周期性喂环境数据 | 串口每隔几秒打印一行 eCO2/TVOC：对着器件哈气或喷一点酒精（远离电路板），TVOC 应在十几秒内明显上升、之后缓慢回落。数据没就绪时 `SYS_CCS811_DataReady` 返回 0，不会打出新行。 | ☐ |
| DHT11：单总线，锁定中断 + 1Hz 节流 + 重试 | 串口每轮打印一行：r = 0 且 T 随环境变化（手捂上去升一两度）；把 raw 五个字节打出来，读失败时能一眼分出“没应答”还是“时序被打断”。连续 20 轮成功率应在 95% 以上。 | ☐ |
| ADC 两路：光敏 PF7(ADC3_IN5) 与 MQ-135 原始值 | 串口打印原始值与毫伏值：遮住光敏原件，light 明显变化；对着 MQ-135 探头哈气（或靠近酒精棉），mq135 的毫伏值在几十秒内上升、离开后缓慢回落。用万用表量同一脚，读数与 `SYS_ADC_ToMilliVolt` 打印值应在 ±50mV 内。 | ☐ |
| 统一“无效值不打进帧”的采集接口 | 拔掉任意一颗器件（或拔 DHT11 数据线）后看打印：`valid` 位图对应位变 0、该路不再出现在后续组帧里，其余 5 路照常出数；插回去该位自动恢复。据此判定“无效值不打进帧”确实生效。 | ☐ |

**本阶段完成判定**：本阶段的产物：每一路都有一个“读一次、返回成功与否”的函数，成功给值、失败给无效标记，绝不用上一次的旧值或 0 冒充真值。6 路分别是：BMP280（气压 + 温度，I2C1 0x76）、BH1750（光照 lx，I2C1 0x23）、CCS811（eCO2/TVOC，I2C1 0x5A）、DHT11（温度 + 湿度，PG9 单总线）、MQ-135（空气质量原始 ADC）、光敏（ADC3_IN5 = PF7）。做完这一阶段，你手里应有一个“采集任务每 2 秒打完 6 路、串口能逐路看到成功/失败与数值”的可验证状态。

### 阶段 5｜数据处理与阈值：从原始值到能报警的干净数

**这一阶段要交什么**：把采集来的原始值做滤波、去野值、判阈值、打包告警位，并把量纲换算成整数（温度湿度 ×100、气压 ×10）。

| 里程碑（每个动作） | 验收判据（怎么算过） | 完成 |
|---|---|---|
| 滤波：滑动平均 + 中值，抑制单点跳变 | 串口同时打印“原始值 / 平均后 / 中值后”三列：正常时三者接近；用手指快速弹一下 DHT11 或让光敏闪一下手电，原始值出现一根大毛刺，中值列基本不动、平均列只轻微抬一下。 | ☐ |
| 野值剔除：和中值/上次值比，太离谱就丢 | 串口打印 `reject` 计数：正常运行时它长时间为 0；用打火机/电烙铁靠近温度探头再迅速移开，或在 DHT11 中途拔线再插，`reject` 计数增加而曲线不断点。 | ☐ |
| 量纲与倍率：温度湿度 ×100、气压 ×10 | 拿已知值验证：串口打印 `T=25.60`、`H=60.30`、`P=1013.2`（用计算器核对换算）；把温度故意取负值 -5.00，打印仍为 `-5.00` 而不是 `650.36` 或 `-5.-0`。 | ☐ |
| 阈值判定 + 回差（迟滞），让告警不抖 | 验收要能“卡在边界上”：把阈值临时改成 `T_LIMIT_X100 = 2600`（26.00℃）并用手捂探头，看着打印在 25.9x~26.0x 之间来回时 `alarm` 只翻转一次；松手降到 25.00 以下才变回 0。若来回乱翻，说明回差没生效或用了 `>=`/`<=` 写成两次比较。 | ☐ |
| 告警位打包：一个字节带 6 路状态 | 人为造每一个位：手捂温度 → 打印里 alarm 的 0x01 位出现；用手电照光敏 → 0x08 位出现；两路同时超限时打印出 0x09。挪开后逐位消失。 | ☐ |
| 处理任务：纯计算 + 不阻塞 + 统计计数 | 给处理任务单独看一条证据：串口每轮一行 `[处理] valid=... alarm=... T=...`，且这一行出现的频率与采集任务一致（每 2 秒一行）。拔掉某颗器件后，这一行照常出现但对应 valid 位为 0——说明处理任务不会因为某一路挂了就停摆。 | ☐ |

**本阶段完成判定**：本阶段的产物：一个纯计算的“处理任务”——输入是阶段 4 的 SensorMsg_t，输出是 6 个定点整数 + 1 个告警位字节。它必须做到：不阻塞、不访问硬件、读不到的数不进结果；超限置位、回到阈值以下（带回差）才清位，避免在阈值上下抖动时告警疯狂翻转。做完这一阶段，你可以在不动任何硬件的情况下，用“注入一个假值”把告警路径完整走一遍。

### 阶段 6｜协议组帧与 CRC：20 字节定长帧

**这一阶段要交什么**：把处理好的 6 个整数按固定格式拼成 20 字节帧，算出 CRC16-MODBUS，并学会用库里的组帧/校验/拆包接口自检。

| 里程碑（每个动作） | 验收判据（怎么算过） | 完成 |
|---|---|---|
| 认清 20 字节帧：偏移表与三个“别搞混” | 你能不看代码把偏移表默画出来（含 ×10、大端、CRC 低字节在前三点），并与 `sys_frame.h` 第 35~78 行逐条对上。 | ☐ |
| 用 SYS_FRAME_BuildEnv 组一帧（首选） | 串口打出的 20 个字节应符合：`AA 55 01 0C 0A 00 17 8E 27 94 01 40 00 0F 03 2C xx xx 55 AA`（其中 0A00 = 2560、178E = 6030、2794 = 10132、0140 = 320、000F = 15、032C = 812），CRC 两个字节由库算出。n 必须是 20。 | ☐ |
| 自己拼一遍 + 算 CRC，确认你懂每个字节 | 手拼的 20 字节与上一步 `SYS_FRAME_BuildEnv` 的输出应**逐字节相同**（同一组输入）。不一致就先比前 18 个字节找数据错，前 18 个相同而 CRC 不同就是 CRC 范围或字节序错。 | ☐ |
| 上板自检：SYS_FRAME_Verify 必须返回 0 | 串口每帧一行 `frame verify OK`；故意把 `f[17]` 异或 0x01 再 Verify，应打印 `FAIL rc=4`（CRC 错）；故意把帧长传 19，应打印 `rc=3`（长度不符）。两种错都能被区分出来。 | ☐ |
| 发送前那一刻的组帧位置：处理结果 → 帧缓冲 | 串口稳定的 `[组帧] 20B ok` 每 2 秒一行。把某路的值手工改成越界数（如 light 传 70000 被截断成 4464），Verify 仍然 OK 但数值变了——说明校验只能证明“字节自洽”，不能替代量程检查。 | ☐ |
| 收侧状态机与重同步：Feed/Poll/Get 怎么配 | 自环测试应打印出与发送端一致的 T/P/light，`err` 计数不增长。再做一次“两帧连发”：把两帧首尾相接 Feed 进去，应能取出两帧、`err` 不变；把帧中间少喂一个字节（模拟丢字节），应取不出帧且 `err` 增长——说明重同步在干活。 | ☐ |

**本阶段完成判定**：帧格式（《检测数据端设计.md》§5）：`AA 55 \| CMD \| LEN \| DATA(12) \| CRC16-MODBUS(2) \| 55 AA`，整帧 20 字节。CMD = `SYS_FRAME_CMD_ENV` 0x01，LEN = `SYS_FRAME_ENV_LEN` 0x0C。数据段全部大端，段内偏移 `SYS_FRAME_ENV_TEMP_OFF` 0 / `HUMI_OFF` 2 / `PRESS_OFF` 4 / `LIGHT_OFF` 6 / `TVOC_OFF` 8 / `MQ135_OFF` 10，对应整帧 4/6/8/10/12/14；CRC 在整帧 16/17（**低字节在前**），帧尾 18/19。本阶段的产物：一个 `SYS_FRAME_BuildEnv` 组出来的帧，以及一段能证明“它自洽、能被重新拆开”的自我验收代码。

### 阶段 7｜LoRa 发送：把帧交给 E22

**这一阶段要交什么**：把组好的 20 字节帧通过 E22 模块发出去：认准 UART、控制脚与模式，按节奏发、出错要能重试、别把模块灌爆。

| 里程碑（每个动作） | 验收判据（怎么算过） | 完成 |
|---|---|---|
| 初始化与模式：先认模块，再切透传 | 串口应依次看到 `E22 init=0`、`to CONFIG=0`、`AT ok`、一行配置字符串（含地址/信道/网络ID）、`back to TRANSPARENT=0`。两端互通要求地址、信道、网络ID 三项完全相同——把两边的 cfg 打印放一起对比。 | ☐ |
| 发送：AUX 忙就别灌数据 | 串口每 2 秒一行 `[发送] 第 N 帧已发出`，N 单调递增且与 LED 闪烁节奏一致。拔掉天线座旁的 AUX 线（或把 AUX 拉高）后，应看到 `AUX 一直忙，本帧放弃`，`s_tx_fail` 增长——说明忙判定真的在起作用。 | ☐ |
| 发送节奏：定周期 + 帧间隔，别把空中灌满 | 串口/上位机统计：一分钟内 `s_tx_ok` 增加约 30 次（2s 一帧），不是几百次。把 `SEND_PERIOD_MS` 改成 100 试一下，能看到发送计数暴涨、板2 侧坏帧计数同时上升——这正说明过密会丢帧。 | ☐ |
| 丢包与超时：自己造一个“没发成功”的判据 | 人为把板2 断电（或拔掉板2 天线），10 秒内板1 的 LED3 点亮、串口打出 `[链路] 10s 未收到对端`；板2 上电后 LED3 熄灭、不再打印。这段时间 `s_tx_ok` 仍在涨——正好证明“发成功 ≠ 对端收到”。 | ☐ |
| 调试出口：把“线上字节”与“本地数值”并排打印 | 串口每次发送前三行成组出现，且第三行 `n=20`。把 `[帧]` 那行的第 8、9 字节与 `[值]` 行的 P 对照（1013.2 hPa → 2794 十进制 → 0x0AEA），能用计算器验证一致。 | ☐ |

**本阶段完成判定**：本阶段的产物：发送任务里一句 `LORA_E22_Send(f, 20)` 能把帧发出去，并且你有一套“看得见”的验收方式（对着板2 或示波器/逻辑分析仪）。关键约束：LoRa 走 `SYS_LORA_UART` = `SYS_USART_3`（PB10/PB11），控制脚 M0/M1/AUX = PB0/PB1/PB2，波特率 `SYS_LORA_BAUD` = 9600 8N1；业务收发前模块必须处于 `LORA_E22_MODE_TRANSPARENT`。

### 阶段 8｜本地显示与交互：OLED、按键、蜂鸣器

**这一阶段要交什么**：把处理结果交给 OLED 显示任务、用 4 个按键翻页、超限时用蜂鸣器报警；界面排版由 AI 完成，你负责数据通路、按键事件与验收。

| 里程碑（每个动作） | 验收判据（怎么算过） | 完成 |
|---|---|---|
| OLED 初始化与“屏亮了”的最小验收 | OLED 第一行出现 `BOARD1 SENSOR`，第三行出现 `T=25.60`。串口 `OLED init=0`。若屏不亮但 init 返回 0，看 `SYS_OLED_ErrCount()`：它在涨 = 写入失败（查上拉/地址/总线被占），恒 0 = 写成功但屏侧问题（查供电与对比度/接线）。 | ☐ |
| 数据交给显示任务：共享快照 + 脏标志 | 改动任意一路数据（比如手捂温度探头），OLED 上的数值在 1 秒内跟着变；把传感器全部拔掉，显示任务照旧刷屏（显示的还是上一帧/无效标记），不会卡死。用逻辑分析仪看 I2C1：只有脏页被写，整屏刷新不会每次都出现。 | ☐ |
| 按键翻页：KEY_Scan 取事件、只在事件时换页 | 按 KEY1：串口打印 `key id=0 page=1`，OLED 换到第 2 页；连按 3 次回到第 1 页（0→1→2→0）。按 KEY2 反向。手指按住不放：只打印一次（不连发）。同时蜂鸣器每按一下短响一声。 | ☐ |
| 蜂鸣器告警：告警位驱动，带确认与静音 | 造一个真实告警（把温度阈值临时调到当前温度以下），蜂鸣器按 100ms 响/停循环；按 KEY4 后蜂鸣器立刻停、OLED 上出现 `MUTE`；再按一下恢复。移走告警源后告警位清掉，声音也跟着停。 | ☐ |
| 显示任务的验收清单（AI 的界面怎么算接对了） | 拔掉 DHT11 后 OLED 对应位置显示 `--`（不是 0、也不是上一次的 25.6）；造告警后同屏出现 `ALM` 且蜂鸣器响；连续观察 1 分钟，I2C1 上不出现“每秒整屏刷新”的规律波形。 | ☐ |
| 显示任务的调度位置：优先级、周期与看门狗 | 用 Keil 的 RTX/FreeRTOS 任务列表或自己打印 `uxTaskGetNumberOfTasks()`/各任务运行计数，能看到 Display 任务的运行时间占比明显低于 Sensor/Comm；把 Display 优先级临时提到 4 再观察，采集周期会开始抖动——反证优先级设置的作用。 | ☐ |

**本阶段完成判定**：本阶段的产物：一个独立的显示任务——它从共享快照里取最新一行数据、按页显示、按键翻页、告警时响蜂鸣器。硬件事实（照库里的宏）：OLED 走 I2C1，SCL = PB8、SDA = PB9，地址 `SYS_OLED_I2C_ADDR` = 0x3C，初始化 `SYS_OLED_Init(SYS_I2C_1, 0x3C)`；按键 `KEY1` = PA0、`KEY2` = PE2、`KEY3` = PE3、`KEY4` = PE4（`KEY_Scan` 返回 id 0~3，无按键返回 `KEY_NONE`）；蜂鸣器 `BEEP_PORT` = GPIOF、`BEEP_PIN` = GPIO_Pin_8。**注意：I2C2 的 PB10/PB11 与 LoRa 的 USART3 同脚，OLED 只能用 I2C1。**

### 阶段 9｜联调验收：与板2 对接、跑 30 分钟

**这一阶段要交什么**：把板1 与板2 接起来跑通整条链路，开看门狗与故障现场记录，连续跑 30 分钟看水位与丢帧，最后按清单逐条签收。

| 里程碑（每个动作） | 验收判据（怎么算过） | 完成 |
|---|---|---|
| 两板对接：帧能从板1 到板2 并转发上位机 | 板1 `[发] seq=N` 与板2/上位机侧的序号一一对应、连续递增；Qt 曲线上能看到温度随环境变化而不是一条直线。三处同一时刻的 T 值一致（允许 1 个采样周期的滞后）。 | ☐ |
| 连续跑 30 分钟：看水位、数丢帧、记重启 | 30 分钟后：`tick` 单调增长到约 1800000（30 分钟 = 1800 秒）；`tx_fail` 增长很慢（< 5%）；`q_sensor` / `q_result` 在 0~1 之间波动而**不是**稳定在满值 4；DHT11 失败次数占比 < 5%；全程 `SYS_WDG_ResetCause()` 里没有新的 `SYS_WDG_RST_IWDG`。 | ☐ |
| 开看门狗：心跳汇总 + 报到纪律 | 验收要能**故意造一次卡死**：在采集任务里插入 `for (;;) { }`（或用调试器暂停该任务），4 秒内板子应复位；复位后串口第一段 `SYS_WDG_ResetCause()` 解码里出现 `SYS_WDG_RST_IWDG`（独立看门狗复位）。删掉死循环后，连续跑 30 分钟不再复位。 | ☐ |
| 故障现场：SYS_FAULT_* 留下 PC 与 CFSR | 故意制造一次故障（临时写 `int a = 1, b = 0; vol = a / b;`，前提是 `SYS_FAULT_DIV0_TRAP = 1`），串口应出现 `--- FAULT ---` 与一行现场报告；Keil Watch 里 `SYS_FAULT_Record.type` 非 0、`pc` 指到那一行附近。删除后 `SYS_FAULT_Happened()` 返回 0。 | ☐ |
| 验收清单：逐条签收，不许“差不多” | 清单上 10 条全部有对应证据；`[签收]` 行里 `frame20` 与发送次数同量级、`verify_ok` 与之一致、`wdg_rst` 不再出现新的看门狗位、`fault=0`。有一条打不了勾就如实记下来，作为下一轮的工作项，而不是把阈值放宽凑过去。 | ☐ |

**本阶段完成判定**：本阶段的产物不是新功能，而是**证据**：板2 能收到板1 的每一帧并转发给上位机（Qt 曲线连续、无断点）；连续 30 分钟运行不重启、不卡死、丢帧率在可接受范围；一旦硬件层出问题能留下现场（`SYS_FAULT_*`）与复位来源（`SYS_WDG_ResetCause`）。这一阶段最忌讳“看着还行就算过了”——每条验收都要能指出“这一行打印/这一条曲线/这一个计数器”作为证据。
