### 阶段 4｜LoRa 接收与协议解析

**这一阶段要交什么**：让板2 真的收到板1 的 20 字节环境帧：LoRa 初始化、收包、CRC16 校验、坏帧重同步，并把它变成可转发的数据。

| 里程碑（每个动作） | 验收判据（怎么算过） | 完成 |
|---|---|---|
| LoRa 上电自检：先证明模块认得上 | 串口打印 LORA_E22_Init() = 0、AT -> 0、mode -> 0；把模块电源拔掉重试，能看到返回 1 或 2 —— 说明自检真的在测。 | ☐ |
| 收包：LORA_E22_Recv 的三个返回码 | 板1 每发一帧，这里就进一次 LORA_E22_OK 分支；验收标准是 overflow 计数保持 0（一帧 20 字节远小于 buf[256]，出现 overflow 说明收到的是粘帧，先调 SYS_LORA_FRAME_GAP_MS，而不是加大调用方缓冲——驱动自己的环形缓冲只有 SYS_LORA_RX_BUF_SIZE = 256 字节）。 | ☐ |
| 逐字节喂给帧解析：SYS_FRAME_Feed 与 SYS_FRAME_Get | 给板2 连发两帧（中间不加间隔），两条都能被取出来；把一帧拆成 7+13 两次发，也能取出完整一条。 | ☐ |
| 整帧校验与 CRC16：别信「帧头对了就是对的」 | 故意把板1 侧某一帧的数据字节改一个（比如把温度低字节加 1），板2 侧必须打印 crc error 并丢掉，正确帧计数不受影响。 | ☐ |
| 坏帧之后的重同步：Reset 与 ErrCount 一起看 | 移动 LoRa 天线让链路变差：错误计数开始涨；把干扰去掉后，正确帧计数继续增长、错误计数停住，不需要复位板子。 | ☐ |
| 把环境帧拆成可用的数据，但转发要留整帧 | 打印的温度小数位与板1 侧实际值一致（比如 25.31 打印成 25.31 而不是 25.30 或 -25.31）；6 个值都对得上板1 的显示。 | ☐ |

**本阶段完成判定**：本阶段产物：LoRa 模块自检通过（返回 LORA_E22_OK）、能稳定收到板1 发来的 20 字节帧、能识别并丢弃坏帧、错帧计数在涨而正确帧计数同步在涨。这一阶段结束时，vTaskLoraRx 应该能把「一整帧 20 字节」投进队列，后面阶段 5、6 都只消费这个结果。

### 阶段 6｜Flash 缓存与断网补传

**这一阶段要交什么**：断网时不丢数据：把每一帧连同时间戳写进 W25Q128 的环形日志区，联网后按上位机命令逐条补传。

| 里程碑（每个动作） | 验收判据（怎么算过） | 完成 |
|---|---|---|
| 先认出芯片与分区：W25QXX_ReadID / W25QXX_Init | ID 打印出 0xEF4018（Winbond）或 0xC84018（GD25Q128）之类，且 Init 返回 0；把片选脚悬空会打印 Init 失败。 | ☐ |
| 理解日志区的槽结构：32 字节一槽，正好装下整帧 | 你能算出来：容量 2048 条、绕回周期、以及「一帧 20 字节刚好等于载荷，一点都不剩」这件事。 | ☐ |
| 初始化与写入：LogInit 扫断点，LogWrite 追一条 | 每收到一帧后 W25QXX_LogCount() 加 1；断电再上电后计数保持（不清零），说明 init 找到了断点；写 2048 条以上能看到计数停在容量上、W25QXX_LogLost() 开始增长。 | ☐ |
| 时间戳从哪来：RTC 秒 + 大端写入 | 串口打印 ts 每缓存一条就变大；把板子断电 10 秒再上电，ts 继续往前走（不是从 0 开始），说明走的是 RTC 而不是开机秒数。 | ☐ |
| 读回与统计：LogRead / LogTail / LogStat / LogLost | 写入 5 条后 count=5；用 LogTail 读出来的 ts 与最后写入的那条一致；超过 2048 条后 count 停在 cap，lost 开始增长。 | ☐ |
| 清空缓存：LogClear 与它的擦除代价 | 发一次清空命令，串口能看出「清空」打印前有约 1 秒的停顿；清完 W25QXX_LogCount() = 0；清空前先把缓存开关关掉的版本，清空过程中收到的帧不会被写进去也不会写坏。 | ☐ |
| 补传：0x15 历史帧 / 0x16 启停 / 0x96 进度，以及去重 | 上位机发 0x16(1)：能连续收到 0x15 帧、约 20 帧/秒；同时收到 0x96 进度帧，已发数单调增长、剩余数递减；发 0x16(0) 立即停。把同一批数据补传两次，上位机按时间戳去重后曲线不重复。 | ☐ |

**本阶段完成判定**：本阶段产物：W25QXX_Init 认得芯片、W25QXX_LogInit 扫出写入断点、每收到一帧就写一条 32 字节记录（12 字节头 + 20 字节载荷，正好放下整帧）、能用 W25QXX_LogRead 按序号读回、能响应 0x16 启停补传并按 0x15 逐条发历史帧、每 50ms 一条，同时用 0x96 上报进度。

### 阶段 8｜联调验收

**这一阶段要交什么**：把板1、板2、上位机连成一条链跑起来，用断网、长时间运行和故障注入把问题逼出来。

| 里程碑（每个动作） | 验收判据（怎么算过） | 完成 |
|---|---|---|
| 整链跑通：板1 → 板2 → 上位机 | 上位机曲线连续、与板1 的显示值一致；板1 每发一帧，板2 的 lora_ok 加一、fwd 也加一；拔掉板1 的 LoRa 天线，板2 的 fwd 停止增长。 | ☐ |
| 断网 30 秒：看缓存增长与补传 | 断网 30 秒、板1 每 2 秒一帧，缓存条数大约增加 15 条（按实际帧率算），串口两侧的计数能对上；恢复后补传出来的条数与断网期间缓存条数一致。 | ☐ |
| 补传对账：条数、时间戳、原帧、去重 | 抽查的每条都 crc=0；0x15 帧数量 + 坏记录数 = 冻结总数；上位机去重后条数与缓存条数一致。 | ☐ |

**本阶段完成判定**：本阶段产物：板1 → 板2 → 上位机整链连通并稳定；断网 30 秒能看到缓存增长、恢复后能补传且不重不漏；连续跑够时间后堆与栈都有余量、丢帧数可解释；看门狗与故障现场在需要时真的能咬到、能留下原因。最后形成一份你自己的验收清单。
