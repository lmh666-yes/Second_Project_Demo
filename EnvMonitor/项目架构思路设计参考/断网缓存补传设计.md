# 断网缓存补传设计

板2 断网缓存的补传通路：断网期间的环境帧落在 W25Q128 里，通信恢复或上位机在线时按原始时间戳补送给 Qt 上位机。

**状态：两端都已实现并验证。** 板2 侧 Keil 全量编译 `0 Error(s), 0 Warning(s)`；Qt 侧 `--selftest` 11/11、`--rangecheck` 5/5、`--cmdselftest` 22/22 全 PASS。第 1 至 8 节是设计方案，第 9 节记录实际实现与方案的差异，第 10 节列出未做的部分。

| 缓存开关 | 上位机命令 0x11 可开可关，默认开 | 板2 `Project/main.c:690`、`:1023-1025` |
| 写入 | 环境帧到达且开关打开时写一条（整帧 20 字节 + 原始时间戳） | 板2 `Project/main.c:951-952` |
| 查询 | 命令 0x12 返回转发开关、缓存开关、已存条数、丢失条数 | 板2 `Project/main.c:1031-1040` |
| 清空 | 命令 0x13 擦除 16 个扇区（64 KB，约 0.5~1 s） | 板2 `Project/main.c:1046-1056` |
| 读取 | 读接口由补传任务 `vTaskReplay` 调用（`W25QXX_LogRead`），另有自检项 07 | `FWLIB/inc/w25qxx_log.h`、板2 `Project/main.c` |
| 补传 | 已实现：`0x16` 触发/停止，`0x15` 逐条上传，`0x96` 回报进度 | 板2 `Project/main.c:1105-1153`（任务）、`:1405-1438`（命令处理） |

读接口（`FWLIB/inc/w25qxx_log.h`）：

```c
uint8_t W25QXX_LogRead(uint16_t index, uint32_t *ts, uint8_t *buf, uint16_t *len);
uint16_t W25QXX_LogCount(void);
uint16_t W25QXX_LogCapacity(void);
uint8_t  W25QXX_LogStat(uint16_t *count, uint16_t *cap, uint16_t *head);
uint16_t W25QXX_LogLost(void);
```

`index` 0 表示最老一条，槽 32 字节（12 字节头 + 20 字节数据），16 扇区共 2048 条。20 字节数据正好等于一整帧 `FRAME_TOTAL`，因此补传可以把存下来的整帧直接转发，不需要重新组帧。

## 2 目标行为

1. 断网（MQTT 断、LoRa 断）期间，环境帧继续落 Flash，容量内不丢。
2. 通信恢复或上位机在线时，把积压记录按**原始时间戳**补送给 Qt，历史数据在曲线上落在它真实发生的时刻，而不是补传时刻。
3. 补传过程可被上位机查询进度、可中止。
4. 掉电安全：补传中途断电，重新上电后能继续，已入库的数据不重复。
5. 补传不得与写入互相破坏：补传期间新到的环境帧要么继续正常写入，要么明确丢弃并计数，不能写出半条记录。

## 3 协议扩展

现有命令占用：0x10 设转发开关、0x11 设缓存开关、0x12 查询、0x13 清缓存、0x14 重启。约定请求 0x10~0x7F、应答 = 请求 | 0x80（`FWLIB/inc/sys_frame.h:94`、`:99`）。

新增两条：

| CMD | 方向 | 载荷 | 说明 |
| --- | --- | --- | --- |
| `0x15` 历史帧 | 板2 → Qt | 24 字节 | 4 字节原始时间戳（大端）+ 20 字节原始环境帧 |
| `0x16` 触发补传 | Qt → 板2 | 1 字节 | 0 = 停止，1 = 开始（LEN=0 也可视为开始） |

应答 `0x96` 载荷建议 4 字节：状态（0 空闲 / 1 补传中 / 2 已完成 / 3 出错）、已补传条数低字节、高字节、剩余条数低字节。

历史帧的 LEN = 24，仍在 `SYS_FRAME_MAX_PAYLOAD`（64）以内，帧总长 32 字节。

为什么不复用 0x01 环境帧：上位机需要区分"实时"与"历史"。实时帧驱动曲线刷新与告警判定；历史帧只入库并回填曲线，不参与实时告警（否则一条两小时前的越限数据会立刻触发告警弹窗）。用一个独立命令字最省事，也便于抓包时直接区分。

时间戳格式沿用现有约定 `hh*10000 + mm*100 + ss`（板2 `main.c:947`），落在板2 记录的 `ts` 字段里，补传时原样搬进历史帧的前 4 字节。

## 4 板2 侧流程

状态机三态：`IDLE` / `REPLAYING` / `DONE`，放在补传任务里。

```
IDLE:
  上位机 0x16(1) 或 开机自动（可选） -> 记录快照 total = W25QXX_LogCount()，读指针 i = 0
  进入 REPLAYING

REPLAYING:
  每 50 ms 处理一条：
    r = W25QXX_LogRead(i, &ts, buf, &len)
    r == OK      -> 组 0x15 帧，qt_send_frame() 发送；i++
    r == EMPTY   -> 说明环形队列出现空洞（大扇区擦除连带丢弃过记录），i++ 继续找，不当作结束
    r == CORRUPT -> 跳过并计数，i++
    i >= total   -> 进入 DONE
  上位机 0x16(0) -> 回到 IDLE，保留已补传位置

DONE:
  上报 0x96 状态 = 2；清空已补传部分（见下）；回 IDLE
```

三个必须处理的问题：

- **擦除连带丢弃**：`w25qxx_log` 在整扇区擦除时会一次丢掉同扇区另外 63 条未补传记录，并把这些计入 `s_lost`。因此补传遇到 `ERR_EMPTY` 只能跳过，不能当成"没有更多数据"直接结束，否则积压会卡在空洞处永远传不出去。
- **清空策略**：补传完成后不能无条件 `W25QXX_LogClear()`，因为补传期间新写入的记录会被一起擦掉。两种做法：(a) 补传期间暂停写入（临时把 `s_cache_on` 置 0，结束再恢复），完成后整片清空，做法简单，代价是补传期间新数据丢弃并计数；(b) 只补传到开始时的 `total` 快照，完成后按条数推进环头指针，不丢新数据，但需要在 `w25qxx_log` 增加"按条数出队"接口。建议先做 (a)，把 (b) 留作后续优化。
- **与写入的互斥**：`w25qxx_log` 内部用 `vTaskSuspendAll()` 保护整段写/擦，单次写约 1 ms、整扇区擦除最坏约 50 ms、清空 16 扇区约 0.5~1 s。补传任务只能通过官方接口逐条读，不能在锁外直接操作 Flash。

补传速度：50 ms 一条对应 20 条/秒；2048 条满载需要约 100 秒。若上位机侧串口 115200 且不落盘阻塞，可加速到 10~20 ms 一条，需实测丢帧率后定档。

## 6 验证方式

1. 板2 开机自检增加一项：写入 5 条带已知时间戳的记录 → 触发补传 → 核对上位机收到的 5 条时间戳与内容逐字节一致。
2. 拔掉 MQTT（断网）让缓存累积若干条，恢复后触发补传，检查 CSV 行数与 Flash 条数一致、时间戳是原始时刻。
3. 补传中途断电：重新上电后再补传，检查 CSV 无重复、无缺行。
4. 上限测试：写满 2048 条（约 100 秒不间断），确认 `W25QXX_LogLost()` 从 0 开始增长、补传后剩余条数与丢失计数能对上。
5. 上位机自检脚本 `--cmdselftest` 增加 0x16 与 0x96 的收发用例。

## 7 边界与风险

- 容量上限 2048 条，对应约 34 分钟（1 秒 1 帧）。断网超过这个时间会开始绕圈覆盖，`W25QXX_LogLost()` 会涨，这一点必须在文档和界面上讲清楚，不能让用户误以为"缓存无限"。
- 清空操作会挂起调度器约 0.5~1 s，期间看门狗只能靠硬件兜底；补传若采用"先停写再清空"的策略，同样要接受这段窗口。
- 历史帧只入库不告警，需要在上位机侧明确实现，否则补传会引发一串过期告警。
- 若后续给协议加序号字段，历史帧也应带上序号，便于上位机判断补传是否有空洞（当前设计靠去重与丢帧计数间接判断）。

`sys_frame.h` 新增（写在 `SYS_FRAME_CMD_REBOOT 0x14U` 之后）：`SYS_FRAME_CMD_HISTORY 0x15U`、`SYS_FRAME_CMD_REPLAY 0x16U`、`SYS_FRAME_HISTORY_LEN 24U`、`SYS_FRAME_HISTORY_TS_OFF 0U`、`SYS_FRAME_HISTORY_FRAME_OFF 4U`、`SYS_FRAME_REPLAY_ACK_CMD`（= 0x96）、`SYS_FRAME_REPLAY_ACK_LEN 4U`、`SYS_FRAME_RA_ST/SENT_LO/SENT_HI/REMAIN_LO = 0/1/2/3`、`SYS_FRAME_REPLAY_ST_IDLE/REPLAYING/DONE/ERR = 0/1/2/3`。

板2 实现要点：任务 `vTaskReplay`（栈 256 字、优先级 3，与 `vTaskCmdRx` 同级、低于 `vTaskForward` 的 4），每 50 ms 处理一条；开始时取 `total = W25QXX_LogCount()` 快照，游标 `i` 从 0 起；`ERR_EMPTY`、`ERR_CORRUPT` 与其它错误一律 `s_replay_bad++` 后 `i++`，只有 `i >= total` 才进 `replay_finish()`；历史帧经 `qt_send_frame()` 发送，与转发帧、命令应答共用 `s_qt_tx_mtx`。

与本文第 3、4 节方案不同的地方：

1. 清空只在 `DONE` 发生，顺序是先清空后上报（应答要带清空结果：成功状态 2、失败状态 3）；第 4 节伪码写的是先上报再清空。
2. 收尾后停在 `DONE`，不自动回 `IDLE`（自检需要一个可观察的收尾态，回 `IDLE` 与"停止"无法区分）。下一次 `0x16(1)` 从头开始。
3. 自检第 08 项拆成两段：写 5 条合成记录在调度器启动前，触发补传与收尾在调度器起来之后（补传必须由任务执行）。
4. 第 08 项只在缓存里全是自检记录或为空时运行（逐条核对时间戳只允许 1000~1002 与 101010~101014、条数上限 8）：一轮补传会整片擦除 Flash，不能拿真实断网缓存做自检，而库里没有单条删除接口。第 07 项先写了 3 条，因此实际 `total = 8`。
5. `0x15` 的 LEN 固定 24：先把 20 字节记录字段清零再拷贝。只有自检第 07 项写的文本记录会走补 0 分支，真实缓存恒为 20 字节整帧。
6. 参数非法（LEN > 1 或取值 > 1）回 `0x96` 状态 3，不用 `SYS_FRAME_ST_PARAM`，以保持 `0x96` 载荷恒为 4 字节。
7. 补传中重复收到 `0x16(1)` 只应答当前进度，不重启游标、不打断本轮。
8. 新任务不占心跳报到位，`APP_TASK_COUNT` 保持 3。
9. `vTaskCmdRx` 的命令字清单注释改为"请求 0x10~0x16"，并注明 `0x15` 是反方向（板2 → 上位机历史帧、无应答）。
10. 空缓存收到 `0x16(1)` 也会走一遍 `W25QXX_LogClear()`（16 扇区约 0.5~1 s），未加空表跳过。

上位机侧实现见第 5 节表格，另有一处行为调整：曲线统计量改为按当前缓冲重算（历史点插入中段会让下标平移，累计量无法增量维护），代价是平均/最大值的口径从累计变为容量窗口内。

## 10 尚未做的部分

- 补传期间新到的环境帧只计数不补发（`s_replay_drop`，结束时串口打印），这是清空策略 (a) 的既定代价。
- 板2 侧没有"已补传位置"的掉电持久化：掉电重启后从头补传，去重交给上位机。
- 方案 (b)（按条数推进环头指针、不丢新数据）未实现，需要给 `w25qxx_log` 增加按条数出队接口。
- 加速档未启用：固定 50 ms 一条（约 20 条/秒，2048 条约 100 秒），第 4 节提到的 10~20 ms 需实测丢帧率后定档。
